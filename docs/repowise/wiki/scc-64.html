Circular Dependency: scc-64

I’ll inspect the report-command module boundaries so the refactoring guidance reflects the actual shared APIs rather than only the import graph.

Cycle Description

SCC scc-64 is a parent/child Rust module cycle in the reports command layer:

reports/mod.rs
  ├─ declares and re-exports publish.rs
  ├─ declares and re-exports render.rs
  └─ declares and re-exports scaffold.rs

publish.rs, render.rs, scaffold.rs
  └─ import CLI argument types from reports/mod.rs

The cycle is structural rather than behavioral: mod.rs owns the shared Clap argument definitions and exposes each child module’s command runner, while each child imports its associated argument types from the parent.

Although the SCC includes all four files, the direct cycles are:

mod.rs ↔ publish.rs
mod.rs ↔ render.rs
mod.rs ↔ scaffold.rs

There is no direct sibling-to-sibling import between publish.rs, render.rs, and scaffold.rs.

Files Involved

  • crates/sc-compose/src/commands/reports/mod.rs
    Declares report submodules, re-exports runner functions, and defines ReportsArgs, ReportsSubcommand, and the report-command argument structs.

  • crates/sc-compose/src/commands/reports/publish.rs
    Implements run_reports_finalize and run_reports_publish_manifest; imports ReportsFinalizeArgs and ReportsPublishManifestArgs from the parent module.

  • crates/sc-compose/src/commands/reports/render.rs
    Implements run_reports_render_spec, run_report_catalog, and run_report_render_many; imports ReportsRenderSpecArgs, ReportCatalogArgs, and ReportRenderManyArgs from the parent module.

  • crates/sc-compose/src/commands/reports/scaffold.rs
    Implements run_reports_init, run_reports_smoke, run_reports_index, and run_reports_verify; imports ReportsInitArgs, ReportsSmokeArgs, ReportsIndexArgs, and ReportsVerifyArgs from the parent module.

The SCC contains 65 symbols overall. Its key coupling is the set of shared command-argument types and the parent module’s runner-function re-exports.

Why This Exists

mod.rs acts as both the public module façade and the location for all report CLI schemas. This is convenient because the ReportsSubcommand enum can directly reference every argument type, and callers can import runners from one place.

Each implementation file then needs the matching argument type to translate parsed CLI input into calls to the reporting services. That creates a bidirectional dependency:

  • Parent → child: module declaration and public runner re-export.
  • Child → parent: command-argument type import.

Rust permits this module layout, so it is not necessarily a compilation problem. It is nevertheless an architectural cycle: the façade and implementations cannot evolve independently, and adding or moving a command type risks touching both sides of the boundary.

Refactoring Suggestions

  1. Extract all report CLI argument types into a dedicated leaf module, such as crates/sc-compose/src/commands/reports/args.rs.

```rust // reports/mod.rs mod args; pub(crate) mod publish; pub(crate) mod render; pub(crate) mod scaffold;

pub(crate) use args::*; ```

Then each implementation imports from super::args, not crate::commands::reports:

rust use super::args::{ReportsFinalizeArgs, ReportsPublishManifestArgs};

This removes the child → façade edge while retaining the existing external API through re-exports.

  1. Keep mod.rs intentionally thin: module declarations, selected re-exports, ReportsArgs, and ReportsSubcommand. Move all individual Args structs to args.rs.

  2. Consider grouping arguments by implementation area if args.rs becomes large:

text reports/ mod.rs publish.rs publish_args.rs render.rs render_args.rs scaffold.rs scaffold_args.rs

mod.rs can assemble the top-level ReportsSubcommand from these leaf types without becoming the owner of every command schema.

  1. Avoid moving reporting business logic into mod.rs. The existing crate::reporting::* services are the correct lower-level dependency; command modules should remain adapters that parse arguments, call services, and format output.

  2. Add an architectural check that prevents command implementation modules from importing crate::commands::reports::{...}. Allow imports only from reports::args or sibling-local argument modules, ensuring this SCC does not return as new report commands are added.
