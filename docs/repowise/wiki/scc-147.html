Cycle Description

SCC scc-147 couples Python binding conversion helpers with the Python-facing type definitions:

convert.rs → types/mod.rs → {policy.rs, request.rs, results.rs} → convert.rs

types/mod.rs is both a module registry and a re-export façade. convert.rs imports wrapper types through that façade, while the individual type modules import conversion helpers back from convert.rs. results.rs also reaches into the façade and directly into policy.rs, creating additional paths within the same strongly connected component.

The cycle covers 192 symbols. It does not necessarily prevent Rust compilation, but it makes ownership of Python-boundary conversion logic unclear and causes small changes to wrappers, registration, or conversions to fan out across the component.

Files Involved

File Role in the cycle Key dependencies
bindings/python/src/convert.rs Converts Python values to and from sc_composer domain values. Imports re-exported wrapper types from crate::types.
bindings/python/src/types/mod.rs Declares type submodules, re-exports their public crate-level wrappers, and registers PyO3 classes. Owns policy, request, and results module inclusion and re-exports.
bindings/python/src/types/policy.rs Defines policy-related PyO3 wrappers and representation helpers. Imports path, metadata, pass, profile, variable, and JSON conversion helpers from convert.
bindings/python/src/types/request.rs Defines request-related PyO3 wrappers and request display helpers. Imports policy wrappers/helpers and request-input conversion helpers from convert.
bindings/python/src/types/results.rs Defines result-related PyO3 wrappers. Imports JSON conversion helpers from convert, PyVariableName through types, and python_bool_repr from policy.

Why This Exists

The cycle reflects a reasonable but overlapping responsibility split:

  • convert.rs needs concrete Python wrapper types such as PyVariableName, PyProfileName, PyConfiningRoot, PyPassConfig, and PyNamedTemplateAsset to extract typed Python inputs.
  • Policy, request, and result wrappers need shared conversion functions to translate Python collections and JSON-like data into sc_composer values.
  • types/mod.rs centralizes public(crate) re-exports and class registration, so importing crate::types::* implicitly depends on every declared type module.
  • results.rs uses cross-type presentation utilities (PyVariableName and python_bool_repr) rather than owning or importing a narrower shared utility surface.

In short, conversion code and wrapper definitions are mutually dependent, while the types façade broadens otherwise narrow dependencies into a five-file SCC.

Refactoring Suggestions

  1. Introduce a lower-level conversion module that does not import PyO3 wrapper structs.

Move generic conversions—JSON conversion, string/map extraction, path coercion, and primitive validation—into a module such as bindings/python/src/conversion/primitives.rs. policy.rs, request.rs, and results.rs can depend on it directly without requiring convert.rs to import types.

  1. Move wrapper-specific extraction next to the wrapper types.

Functions such as extracting PyNamedTemplateAsset, PyProfileName, PyConfiningRoot, PyPassConfig, and PyVariableName should live in their owning type modules or in narrowly scoped modules such as types/assets.rs and types/names.rs. This removes convert.rs → types/mod.rs.

  1. Avoid importing the types façade from internal modules.

Replace use crate::types::PyVariableName in results.rs with a direct sibling import, such as use super::policy::PyVariableName, if that matches ownership. Internal code should import defining modules directly; reserve types/mod.rs re-exports for the crate’s external internal-facing API and registration.

  1. Extract representation helpers from policy.rs.

Move python_bool_repr, python_string_repr, and python_option_string_repr into a dependency-neutral formatting module, for example python_repr.rs. Then request.rs and results.rs no longer depend on policy.rs for formatting-only behavior.

  1. Reduce types/mod.rs to module declaration and registration.

Keep mod declarations and register, but avoid using its broad re-export layer from implementation modules. If re-exports remain useful, treat them as a façade for top-level callers only.

A target dependency direction would be:

conversion primitives / representation helpers
        ↑              ↑
 policy.rs   request.rs   results.rs
        ↑       ↑          ↑
     types/mod.rs (registration and optional façade)

This makes conversion utilities independently reusable, keeps wrapper ownership local, and removes the back-edge from conversion code into the aggregate types module.
