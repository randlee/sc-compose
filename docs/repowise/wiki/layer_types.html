Layer: Types

I’ll inspect the Types module and its immediate consumers to ground the architecture page in the actual interfaces and flow.

Overview

The Types layer is the Python binding’s boundary-model layer, translating Python-facing configuration, requests, and results into validated sc_composer domain values and back into Python objects. It defines the PyO3 classes that make the native composition library usable through a stable, typed Python API, while keeping rendering and orchestration in the Application layer.

Key Components

  • bindings/python/src/types/mod.rs is the layer’s edge connector. It re-exports all Python wrapper types internally and registers every class on the _native PyO3 module.
  • policy.rs wraps configuration and identity concepts: VariableName, ProfileName, ConfiningRoot, ResolverPolicy, ComposeMode, ComposePolicy, and PassConfig. Constructors validate Python inputs, normalize path-like values, and convert invalid domain values into Python errors.
  • request.rs defines input envelopes for native operations. ComposeRequest carries root confinement, composition mode, variable maps, optional guidance and prompts, policy, and runtime; LoadedTemplateRequest and NamedTemplateAsset support in-memory template rendering.
  • results.rs defines read-only Python views over sc_composer outputs, including resolution, composition, validation, parsing, expansion, initialization, verification, diagnostics, and rendering results. It also exposes the standalone Renderer wrapper.

Data Flow

  1. Python callers construct Types-layer objects such as ComposeMode, ComposePolicy, and ComposeRequest.
  2. Constructors and conversion helpers validate names, paths, JSON-compatible values, variable maps, pass metadata, runtime kinds, and confinement roots before storing native sc_composer values in each wrapper’s inner field.
  3. The Application layer (functions.rs) accepts these typed request wrappers and calls sc_composer operations such as compose, validate, resolve_template_path, expand_includes, render_loaded_template, and verify.
  4. Native results are wrapped as Types-layer result classes before crossing back into Python. Getters expose paths as strings, diagnostics as Diagnostic objects, variable provenance as string maps, and JSON-like data as Python dictionaries.
  5. Errors encountered during input conversion or native execution are mapped by the surrounding conversion and error facilities into Python exceptions rather than leaking Rust-specific error types.

Architecture Notes

The layer depends on the Application layer’s shared conversion, enum, and error adapters, while the Application layer depends on Types for the request and result objects used by exported functions. This bidirectional relationship is intentional at the binding boundary: Types owns API shapes, while Application owns operation dispatch.

mod.rs is the public registration seam. Adding a new Python wrapper requires both implementing its PyO3 class and registering it there; otherwise the type remains unavailable from _native.

Types wrappers generally clone native values at API boundaries. This keeps Python objects independent of temporary Rust references and presents immutable, getter-oriented result objects to callers.

The layer preserves compatibility where native behavior has evolved. For example, ExpandedTemplate.frontmatters retains a legacy single-frontmatter view, while frontmatter_passes exposes the full multi-pass representation.
