Overview

render_request.rs is the Application-layer edge connector that translates CLI arguments, template-pack metadata, and input sources into sc_composer::ComposeRequest values consumed by rendering, resolving, validation, verification, examples, and template commands. Because cross-layer callers import it, it forms part of the CLI application’s effective interface to the pure sc-composer library.

This is a high-activity, high-complexity hotspot. Changes here can alter request semantics, security confinement, input precedence, multi-pass behavior, and diagnostics across several commands.

The module centralizes conversion from CLI-specific types (CommonArgs, InputArgs, RenderBehaviorArgs, and PassInputArgs) to composer-domain types. It also owns validation that must happen before composition: mode-specific required options, profile-name validation, mutually exclusive text sources, and the single-read constraint for standard input.

Public API

All exposed functions are pub(crate), intended for command modules within sc-compose.

Function Produces Purpose
build_request ComposeRequest Builds a normal file- or profile-mode request from common CLI arguments, supplied blocks, and template defaults.
build_multi_pass_request ComposeRequest Builds a request with per-pass PassConfig defaults and a union of pass inputs.
build_named_request ComposeRequest Builds a file-mode request from a resolved TemplatePack; runtime is deliberately unset because the pack supplies the template context.
read_block_pair (Option<String>, Option<String>) Reads optional guidance and prompt blocks.
read_block_pair_with_extra_stdin_reads (Option<String>, Option<String>) Performs the same read while accounting for another caller that may consume stdin.

build_request and build_multi_pass_request perform the same core assembly:

  1. Canonicalize the requested root into ConfiningRoot.
  2. Convert CLI mode and runtime enums into composer equivalents.
  3. Load direct variables, variable files, and environment-derived variables.
  4. Attach caller-provided defaults and optional guidance/prompt content.
  5. Derive ComposePolicy from strictness and unknown-variable flags.

build_multi_pass_request additionally creates one PassConfig per pass. A pass number of 0 is replaced with the composer’s default pass number. Its vars_input is the merged union of all pass variables, while each pass’s loaded variables are retained as that pass’s defaults.

Dependencies

  • sc_composer provides the request model and domain validation: ComposeRequest, ComposeMode, ComposePolicy, ConfiningRoot, profile/runtime types, variable types, diagnostics, and recovery hints.
  • cli provides the CLI-layer argument enums and structs converted by this module.
  • template_store::TemplatePack supplies a resolved template path, root, and input defaults for named-template execution.
  • var_file loads or parses structured variable input from files or stdin.
  • CommandError converts filesystem, parsing, and configuration failures into CLI-facing diagnostics.
  • anyhow adds contextual error messages, especially for root canonicalization.
  • Standard-library I/O and filesystem APIs read stdin, text blocks, and environment variables.

Primary callers include commands/compose.rs (run_render, run_resolve, and run_validate), commands/verify.rs, plus examples and template command paths. Those callers should treat successful construction as the boundary after which they can invoke the composer without reinterpreting CLI input.

Usage Notes

Request construction and mode validation

compose_mode enforces the CLI contract before constructing a request:

  • Mode::File requires --file; missing it returns ErrConfigMode with a configuration recovery hint.
  • Mode::Profile requires either --agent or --agent-type; --agent takes precedence when both are present.
  • Profile names are validated through ProfileName::new, so callers should not bypass this module with unchecked strings.
  • confining_root canonicalizes the root before handing it to the composer. This makes template resolution operate within a validated filesystem boundary rather than a raw path.

Variable source precedence

For ordinary inputs, inline --var entries are loaded first and each subsequent variable file is extended into the same BTreeMap. Later sources therefore overwrite earlier entries with the same normalized variable name.

For a pass, inline pass variables are loaded before that pass’s variable files, with the same overwrite behavior. In multi-pass mode, collect_pass_union iterates passes in order; variables from later passes overwrite matching variables from earlier passes in the request-wide union.

Environment variables are separate in vars_env, rather than merged into file or inline inputs. Only variables whose names start with env_prefix are included. Built-in variable names preserve their case; all other stripped names are lowercased before validation. This distinction is important when diagnosing collisions or deciding which input channel should supply a value.

Guidance, prompt, and stdin

Guidance and prompt content can come from either an inline argument or a file, but not both for the same block. The module reports ErrConfigParse if --guidance is combined with --guidance-file, or if --prompt is combined with --prompt-file.

- means stdin for variable files, guidance files, and prompt files. Since stdin is a one-shot stream, read_block_pair_with_extra_stdin_reads counts all requested reads and rejects any total above one with CommandError::stdin_double_read().

For example, this is valid because only one source reads stdin:

sc-compose render --var-file - --guidance "Review the following"

This is rejected because both sources attempt to consume stdin:

sc-compose render --var-file - --prompt-file -

A caller that already plans to read stdin should use read_block_pair_with_extra_stdin_reads(..., 1) so block selection cannot accidentally consume it again.

Error behavior

Configuration and input failures are consistently converted to CommandError with diagnostic codes:

  • Invalid roots, block reads, environment-derived names, and variable-file reads use ErrConfigParse.
  • Missing mode-specific arguments use ErrConfigMode.
  • Invalid inline variable names include a recovery hint describing the permitted characters.

When modifying this hotspot, preserve those mappings and hints: callers and JSON-oriented CLI tests may rely on structured diagnostic behavior, not only message text.
