Guided Tour

How to take this tour

This is an ordered walk from the repository’s entry points inward, descending from CLI and application surfaces toward shared types, tooling, and verification. Each stop builds on the earlier ones so you can follow how inputs become typed operations and observable results.

The tour

Step 1: README.md

The overview introduces the repository’s end-to-end shape before you encounter individual implementation boundaries. Use it as the map for the entry points and layers explored in the remaining steps; begin at README.md.

Step 2: main.rs

The orchestrator is the CLI application entry point: it parses command-line input, initializes observability, dispatches commands, selects human or JSON output, and exits with the selected code. With the repository map from Step 1 in mind, this is the first concrete place to trace a user invocation into the application; open crates/sc-compose/src/main.rs.

Step 3: lib.rs

The public library entry point exposes composition APIs for rendering, resolution, validation, verification, diagnostics, and workspace initialization. Where Step 2 controls a process-level CLI run, this file provides the reusable composition surface that callers—including other bindings—can invoke directly; inspect crates/sc-composer/src/lib.rs.

Step 4: cli.rs

The parser converts process arguments into typed Cli command configurations for dispatch and related operations. It supplies the structured command input that the Step 2 orchestrator needs, while its typed configurations form the CLI-side counterpart to the composition APIs introduced in Step 3; continue in crates/sc-compose/src/cli.rs.

Step 5: lib.rs

The adapter is the Python _native extension-module entry point, building a PyO3 module that exposes sc-composer functions, errors, enums, types, and built-in variable names. It shows a second application edge beside the Rust CLI: instead of Step 4’s process arguments, Python callers reach the public capabilities surfaced in Step 3; visit bindings/python/src/lib.rs.

Step 6: diagnostics.rs

The diagnostics connector defines stable ERR_*, WARN_*, and INFO_* records plus versioned machine-readable payload envelopes. It gives both the Step 2 CLI flow and the Step 5 Python boundary a common way to communicate structured outcomes across layers; read crates/sc-composer/src/diagnostics.rs.

Step 7: path_utils.rs

The path-boundary connector validates relative paths and serializes PathBuf values as forward-slash strings for CLI, reporting, and JSON consumers. This centralizes a concern that otherwise would be repeated throughout the Step 4 command configurations and Step 2 output paths; examine crates/sc-compose/src/path_utils.rs.

Step 8: types.rs

The contract module defines the validated request, policy, trace, diagnostic, and result types shared across sc-composer and cross-layer callers. It is the common vocabulary beneath the public API in Step 3, the diagnostics in Step 6, and the CLI inputs produced in Step 4; open crates/sc-composer/src/types.rs.

Step 9: atm-nudge.py

The tooling dispatcher resolves an agent’s authoritative tmux pane and produces post-send tmux keystrokes, structured diagnostics, and hook results. After following the runtime-facing Rust and Python edges, this stop marks the shift into Docs & Tooling infrastructure that supports repository workflows; see scripts/atm-nudge.py.

Step 10: policy.rs

The Python types adapter exposes validated sc_composer policy, mode, naming, confinement, and pass-configuration values as PyO3 classes. It carries the shared contracts from Step 8 across the Python boundary introduced in Step 5, using shared coercion helpers to keep Python-facing values aligned; inspect bindings/python/src/types/policy.rs.

Step 11: mod.rs

The reports command module parses reports subcommands into typed arguments and re-exports handlers for command dispatch. It is a focused command-family extension of the parsing and dispatch path established by Steps 4 and 2, while also serving as the CLI layer’s dependency anchor; visit crates/sc-compose/src/commands/reports/mod.rs.

Step 12: repo_boundaries.rs

The boundary test suite verifies repository-level behavior and constraints, with the Python tests living alongside it. It closes the tour by checking the edges you have traced—from the CLI flow in Steps 2 and 4 through the library and Python surfaces in Steps 3 and 5; read crates/sc-compose/tests/repo_boundaries.rs.
