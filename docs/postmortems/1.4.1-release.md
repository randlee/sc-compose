# Post-mortem: 1.4.1 release

## Root cause

We don't durably write down failures when we fix them. Every recurring
failure in this release traces back to a fix that existed only as a chat
message, a memory note, or a "we'll handle it next sprint" — never as a
line in the repo that the next release run would actually hit.

Two concrete instances from this release:

1. **winget publish token.** `release.yml` used `secrets.GITHUB_TOKEN`
   instead of `secrets.WINGET_GITHUB_TOKEN` for the winget-releaser step.
   This broke 1.4.0's automated winget submission too — it was worked
   around with a manual PR to `microsoft/winget-pkgs` (GH issue #418) and
   believed to have been fixed in a "follow-up sprint." `git log -p
   --follow` on `release.yml` showed the wrong secret name unchanged since
   the very first release-engineering commit (`d211103`). No such fix ever
   landed in code. Fixed for real in #466.

2. **Release-gate ancestry check.** `scripts/release_gate.sh` required
   `develop` to be a git ancestor of `main`, which false-positives on any
   sync-only merge commit that exists only on `develop` even when the
   trees are byte-identical. This was a known-shaped problem the first
   time we hit a sync PR during a release, but nothing was written down
   about it, so it cost a full two-PR-cycle detour (#461 then #463) before
   we fixed the actual gate logic in #465.

In both cases the failure mode was known or suspected before this release
and was not written into the repo where it would have prevented a repeat.

## What changed as a result

- `docs/git-workflows.md` — release-track fixes now branch off `main`
  directly (`release/*`), not `develop`; `develop` sync happens after
  publish as housekeeping, not a pre-publish gate. (#464)
- `scripts/release_gate.sh` — ancestry check replaced with a content-diff
  check, so a sync-only merge commit can't false-positive the gate again.
  (#465)
- `.github/workflows/release.yml` + `docs/WINGET_SETUP.md` — correct
  secret wired in, and the doc corrected to state the token requirement
  instead of claiming the default `GITHUB_TOKEN` is sufficient. (#466)
- `docs/release-checklist.md` — corrected the manual-tag instruction,
  which was stale relative to the `gate-and-tag` job that actually owns
  tagging.

## Standing rule

Any fix made during a release — a wrong secret, a bad gate check, a stale
checklist step — gets written into the file/doc it affects in the same
session it's fixed, not described in chat and left to be rediscovered
next release. If a doc claims something is fixed, it must be verified
against the actual code (`grep`/`git log -p`), not trusted at face value.
