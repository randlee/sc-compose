# Sprint P.2 — Go module distribution and consumer handoff

## Goal

Make the P.1 generated `sc-sha` Go package consumable outside this Cargo
workspace, publish it with a reproducible native-library contract, and hand
off exact adoption evidence to `sc-dolt` and atm-core. This sprint does not
modify those external repositories.

**Traceability:** P-R4, P-R5, and P-N2.

## Dependencies and parallelism

P.2 starts only after P.1's public generated contract and drift check are
merged to `integrate/phase-p`. It cannot run in parallel with P.1. It may run
with unrelated work outside the Go adapter/release files, but no other Phase P
sprint may define a second module path, native library layout, or consumer
handoff protocol.

- `bindings/sc-sha-go/go.mod`

## Required work

1. Set the released Go module path to
   `github.com/randlee/sc-compose/bindings/sc-sha-go` and document the Git tag
   convention required for a Go submodule release. Do not create a separate
   shim repository in this phase.
2. Define and implement the native-library release layout used by the generated
   CGo package. It must name every supported OS/architecture pair, carry the
   matching generated interface/checksum, and fail clearly for an unsupported
   target. Release artifacts—not a caller's local Cargo checkout—are the
   external-consumer contract.
3. Extend the release workflow to build, attach, and verify the Go-native
   artifacts for every platform the module advertises. CI must test the module
   from an independent temporary Go module, not only through a local relative
   path in the workspace.
4. Add a release-layout test that proves a generated package's CGo library
   name/path resolves to an artifact for every advertised target and rejects a
   mismatched architecture/library combination before use.
5. Document installation, native-library lookup/linking, supported-target
   matrix, generated-code policy, version compatibility, and the exact typed
   `CalculateHash` / `CalculateCompositionHash` examples. The examples must
   use committed conformance fixtures.
6. Prepare external handoff records for `sc-dolt` and atm-core: module/version
   and tag, supported platform matrix, known vectors, typed error mapping,
   update instructions, and a request for independent adoption/verification.
   Record their response as external evidence; do not merge their source
   changes from this worktree.

## Release contract

The published module must not depend on `go generate`, a checkout of
`sc-compose`, `LD_LIBRARY_PATH` manipulation, or a system-wide manually
installed Rust library for normal consumer use. The generated package selects
only a matching packaged native artifact. If the host is unsupported or the
artifact is absent/mismatched, package initialization/use fails with a
deterministic diagnostic naming the target and remediation; it must not silently
fall back to a different architecture or a duplicate Go hash implementation.

The implementation may use static linking or a packaged shared library, but
P.2 must choose one contract and test it on every advertised target. The choice
is a release concern, not a reason to add handwritten public CGo code.

## Deliverables

- an externally consumable, versioned generated Go module;
- release-built target-native artifacts with tested package resolution;
- an independent consumer-module integration test;
- documentation and handoff evidence for `sc-dolt` and atm-core.

## Acceptance criteria

- [ ] `go get` / Go module resolution identifies the documented submodule and
      version tag; its public Go source is generated by P.1's pinned toolchain.
- [ ] A supported target builds and runs the package from an independent Go
      module with no local Cargo checkout and no `LD_LIBRARY_PATH` setup.
- [ ] Every advertised target has a matching native artifact; mismatch and
      unsupported-target paths fail deterministically without fallback.
- [ ] Release CI verifies the generated source, target artifact layout, and
      independent consumer-module test.
- [ ] `sc-dolt` and atm-core receive precise handoff material and an adoption
      request; their external adoption is tracked separately rather than
      claimed complete by sc-compose.
- [ ] No release or test path weakens Go pointer checks or introduces a second
      hash implementation.

## Required validation

```text
cargo fmt --all --check
cargo test --workspace
cargo clippy --all-targets --all-features -- -D warnings
just lint
just generate-sc-sha-go check
just prepare-sc-sha-go-native
(cd bindings/sc-sha-go && go test ./...)
python3 bindings/sc-sha-go/tests/test_release_layout.py
git diff --check
```

The release workflow additionally runs the independent consumer-module test on
each advertised OS/architecture. A platform is not documented as supported
until that job is green.

## QA handoff

handoff records, and required validation output. Team-lead routes the PR to
quality-mgr. Apply Phase P's sc-lint cleanup and fix-worktree routing before
declaring P.2 complete.
