Observed

FUZZ-015

Minimal template / frontmatter
UC-8 loop: formula = "batch" ... {% for i in range(1, count + 1) %}[[steps]] id = "item_{{{ i }}}" ... needs = ["item_{{{ i - 1 }}}"]{% endfor %}
Input
attach, compose_variables {"count":36}, parent <epic>, ref batch
Expected
FR-23.5 / ADR-0023 UC-4, UC-5: re-running an attach whose beads all exist succeeds and writes nothing; UC-8 generates many steps; no step limit is documented.
Observed
First attach creates 36 beads; every re-run or preview-attach exits 2 with BEADS_PROCESS_OUTPUT_LIMIT ('Beads Attach output exceeded the 65536-byte capture limit') and no receipt. Threshold ~34 minimal steps (fewer with metadata). The 500-step attach fails even on its first run (bd show stderr for 500 missing ids ~101 KB) and a 500-step graph preview-pour fails on bd cook --json (78 KB). Reproduced 3/3 by the coordinator at count=36.
Requirement / ADR
FR-23.5, FR-23.6; ADR-0023 UC-4, UC-5, UC-8, UC-9, Conflict rules
Requirement / ADR follow-up
No new ADR needed for re-run; if a step ceiling remains, document it in ADR-0023 and the bead manual.
Root cause
GraphReader::issues issues one `bd show <parent> <every planned id> --json`; bd v1.3.1 prints ~1.9 KB per existing bead, beyond runner PROCESS_OUTPUT_LIMIT_BYTES (64 KiB per stream). The cook --json read hits the same cap for large formulas.
Recommended fix
Batch bd show reads, and size the capture limit for graph reads (or stream-parse) so attach scales to the documented use cases.
