FUZZ-015

Minimal template / frontmatter
UC-8 loop: formula = "batch" ... {% for i in range(1, count + 1) %}[[steps]] id = "item_{{{ i }}}" ... needs = ["item_{{{ i - 1 }}}"]{% endfor %}
Input
attach, compose_variables {"count":36}, parent <epic>, ref batch
Expected
FR-23.5 / ADR-0023 UC-4, UC-5: re-running an attach whose beads all exist succeeds and writes nothing; UC-8 generates many steps; no step limit is documented.
Observed
First attach creates 36 beads; every re-run or preview-attach exits 2 with BEADS_PROCESS_OUTPUT_LIMIT ('Beads Attach output exceeded the 65536-byte capture limit') and no receipt. Threshold ~34 minimal steps (fewer with metadata). The 500-step attach fails even on its first run (bd show stderr for 500 missing ids ~101 KB) and a 500-step graph preview-pour fails on bd cook --json (78 KB). Reproduced 3/3 by the coordinator at count=36.
Requirement / ADR
FR-23.5, FR-23.6; ADR-0023 UC-4, UC-5, UC-8, UC-9, Conflict rules
Requirement / ADR follow-up
No new ADR needed for re-run; if a step ceiling remains, document it in ADR-0023 and the bead manual.
Root cause
GraphReader::issues issues one `bd show <parent> <every planned id> --json`; bd v1.3.1 prints ~1.9 KB per existing bead, beyond runner PROCESS_OUTPUT_LIMIT_BYTES (64 KiB per stream). The cook --json read hits the same cap for large formulas.
Recommended fix
Batch bd show reads, and size the capture limit for graph reads (or stream-parse) so attach scales to the documented use cases.

FUZZ-016

Minimal template / frontmatter
formula = "one" / version = 1 / type = "workflow" / [[steps]] id = "a" title = "A"
Input
attach request with "parent":"--help" (or "--version"); or relation {"from":"step:a","to":"bead:--db=/nonexistent","type":"related"}
Expected
ADR-0023 Conflict rules / Relation validation: a missing parent is BEADS_GRAPH_PARENT_NOT_FOUND and a missing bead: endpoint is GraphRelationInvalid(bead_not_found). BeadId only requires non-empty, no whitespace.
Observed
Exit 2 failed BEADS_GRAPH_READ_FAILED; argv ['bd','show','--help','--help.inj-a',...] and ['bd','show','--db=/nonexistent',...]: bd parsed the ids as options and, for --db=, opened a different database. Controls with ordinary missing ids give the documented codes. Reproduced 3/3 per variant by the coordinator. No write is reachable.
Requirement / ADR
ADR-0023 Conflict rules, Relation validation; BeadId contract
Requirement / ADR follow-up
No new ADR needed.
Root cause
Request ids are spliced into `bd show <ids...> --json` and `bd dep list <id> --json` with no `--` separator.
Recommended fix
Pass ids after `--` (bd v1.3.1 accepts it) or reject bead ids starting with '-' at the BeadId boundary.

FUZZ-017

Minimal template / frontmatter
{"id": 12345678901234567890123, "amount": 0.10000000000000000001}
Input
no variables; destination absent
Expected
help render 'Appending JSON records' step 2: the object is parsed and re-serialized and only its key order may differ; FR-7 render --append.
Observed
Exit 0; appended {"amount":0.1,"id":1.2345678901234568e+22}. Integers above u64 become lossy floats, long decimals round, 1e2 -> 100.0, -0 -> -0.0. Plain render passes the body unchanged. Reproduced 3/3 by the coordinator; --append does not exist on origin/develop.
Requirement / ADR
FR-7 render --append; FR-8a; help render 'Appending JSON records'
Requirement / ADR follow-up
No new ADR needed; if normalization is intended, the manual must say so.
Root cause
append_json_record parses into serde_json::Value without arbitrary_precision and re-serializes.
Recommended fix
Validate the object but keep the original number tokens (arbitrary_precision or RawValue plus minification).
