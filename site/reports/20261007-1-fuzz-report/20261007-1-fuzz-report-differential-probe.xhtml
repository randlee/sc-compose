FUZZ-013

Minimal template / frontmatter
formula = "re g0" / version = 1 / type = "workflow" / [[steps]] id = "a" title = "A"
Input
render request with "formula_name":"re g0" (also "café", "a+b", "")
Expected
ADR-0023 Decision 1: additive only; Phase R requests parse unchanged. Baseline accepts these requests (exit 0 render/validate/registry preview-pour).
Observed
Head: exit 3 BEADS_REQUEST_DESERIALIZATION_FAILED 'invalid graph formula ...; follow ADR-0023' for every operation, including render, which never uses the name. formula_name "" now gives deserialization failure instead of BEADS_FORMULA_NAME_REQUIRED on pour. Reproduced 3/3 by the coordinator, head vs baseline.
Requirement / ADR
ADR-0023 Decision 1 and Consequences; ADR-0021 FormulaNameRequired
Requirement / ADR follow-up
Decision owner team-lead: either keep the grammar and amend ADR-0021/0023 (documenting the breaking change), or confine the grammar to the uses that need it (registry path, graph metadata).
Root cause
Commit e1b5168 made BeadComposeRequest.formula_name a validating FormulaName newtype, so serde rejects names outside [A-Za-z0-9_][A-Za-z0-9_.-]* during request parsing.
Recommended fix
Validate formula_name only where it becomes a path or bd argument, with a stable code, and keep Phase R parsing unchanged; or record the break in an ADR.

FUZZ-014

Minimal template / frontmatter
formula = "x" / version = 1 / type = "workflow" / [[steps]] id = "a" title = "A {{{ tag }}}"
Input
request k: ref race<k>, compose_variables {"tag":"T<k>"}, rendered_formula <ws>/build/x.formula.toml
Expected
ADR-0023 Atomic apply and Revision: each request's beads come from its own rendered text; GraphApplyFailed means bd wrote nothing.
Observed
Coordinator repro (3 trials): trial 1: a failed receipt (GraphApplyFailed, 'nothing was written') whose own bd create returned ids for the other request's plan; trial 2: a succeeded receipt for ref race20 created a bead titled 'A T21', i.e. the other request's content. Worker saw cross-contamination in 27/27 trials. Deterministic regression via a path-honest fake bd.
Requirement / ADR
ADR-0023 Decision 6, Graph plan, Revision, Errors (GraphApplyFailed); UC-9
Requirement / ADR follow-up
No new ADR needed for the invariant; if a shared rendered_formula is to be unsupported, document and refuse it.
Root cause
graph::run re-reads rendered_formula from disk and bd cooks it by path, and PendingCreate::execute writes then applies the fixed path <rendered_formula>.graph.json, so concurrent requests sharing the path race on both files.
Recommended fix
Hash and cook the bytes this request rendered (private copy), and write the plan to a per-invocation path or hold a lock across render-cook-apply.
