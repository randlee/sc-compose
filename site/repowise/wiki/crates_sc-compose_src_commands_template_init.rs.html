Overview

template_init.rs is the CLI-layer command adapter for template initialization: it consumes parsed template-init/frontmatter-init arguments and template files, then produces frontmatter-prefixed templates with literal values replaced by pass-specific MiniJinja variable tokens.

It exposes the command handlers dispatched by commands::dispatch and delegates document parsing and result types to sc-composer. frontmatter-init uses the library’s existing initializer, while template-init implements multi-pass initialization locally: it validates pass-group input, rewrites matching literals, builds YAML frontmatter, optionally writes the result, and formats CLI or JSON output.

This is a high-activity, high-complexity hotspot. Changes to replacement ordering, overlap detection, frontmatter shape, error codes, or dry-run/JSON behavior can affect both template correctness and CLI contract compatibility.

Public API

  • run_frontmatter_init(args: &FrontmatterInitArgs) -> Result<i32, CommandError>
  • CLI entry point for frontmatter-init.
  • Calls sc_composer::frontmatter_init.

  • In dry-run mode, prints generated frontmatter; with --json, emits an output envelope containing affected path, change state, and discovered variables.

  • run_template_init(args: &TemplateInitArgs) -> Result<i32, CommandError>

  • CLI entry point for template-init.
  • Reads grouped --pass N and --var key=value inputs through parse_pass_inputs.
  • Validates variable names, normalizes pass 0 to the default pass, invokes file initialization, and selects human-readable, dry-run, or JSON output.

Internal implementation types:

  • InitPass

  • Represents one rendering pass and its (VariableName, literal_value) replacements.

  • PlannedReplacement

  • Stores a replacement’s pass, variable name, source literal, and brace count.

  • render_token creates {{ name }}-style tokens; pass N uses N + 1 braces on each side.

  • MultiPassHeader

  • YAML serialization model for a multi-pass frontmatter block, containing pass, required_variables, and literal defaults.

Core helpers:

  • template_init_file
  • Canonicalizes and reads the target file, rejects existing frontmatter unless --force is supplied, applies substitutions, prepends frontmatter, and conditionally writes the result.

  • Returns FrontmatterInitResult, including generated text, discovered variable names, and changed/would_change status.

  • plan_replacements

  • Converts pass variables into replacements and sorts them by descending literal length, then descending pass number.

  • apply_replacements

  • Verifies every requested literal exists, identifies non-overlapping source spans, and rewrites the original text once.

  • build_stacked_frontmatter

  • Produces either the legacy single-pass header or one YAML document per initialization pass.

Usage Notes

A single-pass initialization replaces supplied literals and preserves the legacy frontmatter format:

sc-compose template-init agent.md \
  --pass 1 \
  --var task=test \
  --var team=wyvern

For a file containing deploy test for wyvern, the body becomes:

deploy {{ task }} for {{ team }}

The generated header uses the compatibility shape:

---
required_variables:
  - task
  - team
defaults: {}
metadata: {}
---

Multi-pass initialization emits one frontmatter document per pass and assigns brace depth from the pass number:

sc-compose template-init agent.md \
  --pass 2 --var worktree_path=/home/wyvern/worktrees/wyvern \
  --pass 1 --var team=wyvern

This produces a pass-2 token such as {{{ worktree_path }}} and a pass-1 token such as {{ team }}. Multi-pass headers include each pass’s required variables and literal defaults.

Important behavior and safeguards:

  • At least one --pass N group is required. Each --var must belong to a preceding pass group.
  • Variable names are validated by VariableName; allowed characters are ASCII letters, digits, ., _, and -.
  • Pass 0 is normalized to the configured default pass number.
  • Existing frontmatter is rejected unless --force is given. --force permits rewriting the file’s header, but substitutions still operate over the original complete content.
  • Every specified literal must appear in the source. Missing values fail with ErrConfigParse.
  • Literal replacements are planned longest-first. This prevents a short value such as wyvern from being substituted inside a longer value such as /home/wyvern/worktrees/wyvern.
  • Replacements use source spans calculated before rewriting. Inserted variable tokens are therefore never scanned and modified by later replacements.
  • Duplicate or overlapping literal assignments that cannot receive distinct source spans fail rather than silently assigning the same text to multiple variables.
  • --dry-run does not write the file; it prints generated template text or, with --json, reports would_affect and would_change.
  • JSON output normalizes path separators and uses the project’s standard envelope format.
  • YAML serialization failures are converted to structured command errors instead of panicking.

The test suite covers multi-pass output, legacy single-pass compatibility, longest-first substitution, duplicate-literal rejection, inserted-token safety, missing-value diagnostics, default-pass normalization, and structured serialization failures.
