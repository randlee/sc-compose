File: bindings/python/src/lib.rs

Overview

native is the Application-layer entry point and orchestrator for the Python _native extension module, producing a populated PyO3 module that exposes built-in variable names, errors, enums, types, and callable functions from sc-composer.

The module is intentionally thin: it composes registration routines owned by focused sibling modules rather than implementing Python-facing behavior itself. At extension-import time, native adds BUILTIN_VARIABLE_NAMES from sc_composer::validation as a Python list, then delegates registration of the remaining bindings.

This is a hotspot file with high change frequency and complexity. Changes here can affect Python import behavior, the public native-module surface, and the initialization order of every registered binding.

Public API

Python extension module: _native

The #[pymodule] and #[pyo3(name = "_native")] attributes export this Rust module to Python as _native.

The module initializer returns PyResult<()>; any failure while building the exported list or registering a submodule aborts module initialization and surfaces as a Python import error.

BUILTIN_VARIABLE_NAMES

native exports BUILTIN_VARIABLE_NAMES as a Python list.

Its contents originate from sc_composer::BUILTIN_VARIABLE_NAMES, keeping the Python binding aligned with the core library’s validation vocabulary rather than duplicating the names in the binding layer.

Registered binding groups

The initializer delegates exports to these internal modules:

  • errors::register(module) — installs Python-visible error types or error conversions.
  • enums::register(module) — installs enum bindings.
  • types::register(module) — installs Python classes and related type bindings.
  • functions::register(module) — installs Python-callable functions.

Each registration routine receives the same bound PyModule, so all symbols become direct attributes of _native.

Usage Notes

Python normally reaches this file by importing the compiled extension module:

from sc_compose import _native

print(_native.BUILTIN_VARIABLE_NAMES)

A typical consumer can use the exported constant to inspect names recognized by the underlying composer:

from sc_compose import _native

if "environment" in _native.BUILTIN_VARIABLE_NAMES:
    print("The native layer recognizes the environment variable.")

When extending the Python API, add the implementation to the appropriate sibling module and ensure its register function is called from native. Keep exports grouped by responsibility:

  1. Add conversion-only logic to convert.
  2. Add a new Python class to types, an enum to enums, an exception to errors, or a callable to functions.
  3. Register the new item from that module’s register routine.
  4. If introducing a new binding group, add its module declaration and call its registration routine in native.
  5. Verify that importing _native succeeds, because one failing registration prevents the entire extension module from loading.

Registration order is observable during initialization. If a type, exception, or enum must already exist before another module creates references to it, preserve or deliberately adjust the current order:

  1. Export BUILTIN_VARIABLE_NAMES.
  2. Register errors.
  3. Register enums.
  4. Register types.
  5. Register functions.

Potential pitfalls:

  • Do not duplicate BUILTIN_VARIABLE_NAMES in the Python binding; it must remain sourced from sc_composer to avoid validation/API drift.
  • Treat every ? as import-critical: a failure in PyList::new or any register call makes _native unavailable.
  • Avoid moving CLI concerns or composition logic into this file. Its role is module assembly in the Application layer, while the pure sc-composer library remains the source of core behavior.
  • Because this is a hotspot and subsystem entry point, review changes for accidental removal, renaming, or reordering of exports that downstream Python code may import directly.
