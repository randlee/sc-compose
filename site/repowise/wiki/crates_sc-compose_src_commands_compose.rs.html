Overview

compose.rs is the CLI-layer command orchestrator for render, resolve, and validate operations; it consumes parsed command arguments and composition requests, invokes sc-composer, and produces terminal or JSON output, rendered files, diagnostics, and process exit codes.

This high-activity, high-complexity hotspot centralizes behavior that would otherwise diverge across the render, resolve, and validate subcommands. commands::dispatch::run calls its public crate-level entry points, while this module delegates request construction to render_request and composition semantics to the pure sc-composer library.

Its main responsibilities are:

  • Build single-pass or multi-pass ComposeRequest values from CLI arguments and stdin/file inputs.
  • Enforce CLI-only rules, including profile-only resolution and correct --all/--pass grouping.
  • Preflight templates to inspect stacked frontmatter passes before rendering or validation.
  • Invoke observer-aware library operations so progress/outcome telemetry remains available.
  • Support a custom-delimiter rendering path without changing the library’s normal rendering behavior.
  • Format success payloads, dry-run previews, warnings, validation errors, and exit statuses consistently.

Public API

All externally callable symbols are pub(crate), so they are internal CLI command APIs rather than public crate exports.

run_render

pub(crate) fn run_render(
    args: &RenderArgs,
    observer: &mut dyn CompositionObserver,
) -> Result<i32, CommandError>

Primary render command entry point.

It selects one of three flows:

  1. --all: parses repeated --pass N input groups, counts additional stdin reads needed by --var-file -, builds a multi-pass request, and preflights the root template.
  2. Custom delimiters: when --brace-count or --variable-delimiters is present, builds a normal request and takes the dedicated custom rendering path.
  3. Standard render: builds a request and delegates to execute_render.

For multi-pass templates, --all requires exactly one pass-input group for every root-template pass. A template without stacked headers remains valid with --all, but emits WarnConfigSinglePassAllFallback and proceeds as a single-pass render.

Potential pitfall: --all validation depends on the root template’s frontmatter passes, not just the number of supplied --pass groups. Includes do not alter this root-pass count.

execute_render

pub(crate) fn execute_render(
    request: &ComposeRequest,
    args: &RenderBehaviorArgs,
    observer: &mut dyn CompositionObserver,
) -> Result<i32, CommandError>

Shared standard-render executor. It calls sc_composer::compose_with_observer, combines library warnings with any caller-supplied warnings, emits output, and returns the success exit code.

execute_render_with_extra_warnings is the private implementation used to attach the single-pass --all fallback warning without changing normal composition results.

run_resolve

pub(crate) fn run_resolve(
    args: &ResolveArgs,
    observer: &mut dyn CompositionObserver,
) -> Result<i32, CommandError>

Resolve command entry point. It only accepts profile mode; file mode returns a usage error with ErrConfigMode.

On success:

  • Text mode prints the resolved template path followed by every searched path.
  • JSON mode emits resolved_path, search_trace, and found: true.
  • Paths are normalized with to_forward_slash in JSON output for cross-platform stability.

run_validate

pub(crate) fn run_validate(
    args: &ValidateArgs,
    observer: &mut dyn CompositionObserver,
) -> Result<i32, CommandError>

Validation command entry point. It mirrors render’s multi-pass request construction when --all is supplied, then calls sc_composer::validate_with_observer.

It aggregates warnings and errors for display but returns a status based on report.ok:

  • Success when validation passes.
  • VALIDATION_OR_RENDER_FAIL when validation fails.

Unlike rendering, validation reports diagnostics instead of converting validation failures into CommandError, except for failures that prevent building or executing the request.

Usage Notes

Standard render

A normal render builds a request from the common CLI arguments plus template/input blocks, then uses the library’s standard composition pipeline:

dispatch::run
  → compose::run_render
  → render_request::build_request
  → sc_composer::compose_with_observer
  → emit_render_output

Without --output, rendered text is printed to stdout. With --output path, the text is written to that exact path and the module reports the file’s actual byte count in JSON mode.

Multi-pass render with --all

For a template with stacked frontmatter passes, supply one ordered --pass N group for each root pass:

sc-compose render profile-name --all \
  --pass 1 --var-file first.json \
  --pass 2 --var-file second.json

The module preflights the expanded template before composition to determine the root pass count.

  • Too few or too many pass groups fails with ErrConfigParse.
  • --var-file - is counted before input blocks are read, ensuring stdin is consumed the required number of times.
  • If the template has zero or one root pass, --all is accepted as a compatibility fallback and produces a warning.

Resolve behavior

resolve is specifically a profile lookup operation. Invoking it in file mode is rejected because there is no profile search to perform.

Use JSON output when a caller needs a machine-readable resolution trace:

{
  "resolved_path": "profiles/example.md",
  "search_trace": ["..."],
  "found": true
}

The found field is always true on this success path; unsuccessful resolution is surfaced as a command error instead.

Validation behavior

Validation performs request construction and, for --all, the same preflight checks as rendering. It does not write output.

Text mode prints valid when there are no diagnostics. Otherwise, each diagnostic is formatted with severity, code, message, and optional source location:

[warning] WARN_CODE: message (template.md:12:4)

JSON mode emits valid plus the collected warnings and errors through the shared JSON printer.

Custom delimiters

Custom delimiter rendering is a separate path because it must construct a Renderer with caller-selected delimiters after validation and include expansion.

Supported inputs:

  • --brace-count N creates N opening and closing braces.
  • --variable-delimiters OPEN CLOSE uses the two explicit delimiter strings.

The path validates first, expands includes, finds the root template frontmatter, creates a validated ParsedTemplate, and renders its body with a context assembled in this precedence order:

  1. First root-pass frontmatter defaults.
  2. Request-level default variables.
  3. Generated runtime values: TEMPLATE_NAME, HOSTNAME, USERNAME, RENDER_DATE, and RENDER_TIMESTAMP.
  4. Environment-derived variables.
  5. Explicit input variables.

Later entries overwrite earlier entries with the same name. In particular, explicit input values can override defaults and generated values.

This flow also emits RenderOutcomeEvent to the supplied observer on both success and renderer failure. Validation failures are converted into a rendering/validation command error before renderer construction.

Output and dry-run semantics

emit_render_output handles all normal and custom render output paths.

  • --dry-run never writes a file.
  • Dry-run calculates would_change by comparing rendered bytes with the current derived output file; unreadable or absent files count as changed.
  • File-mode derived paths strip only a final .j2 suffix.
  • Profile-mode derived paths use .prompts/<profile-name>-<ULID>.md when no explicit output path is supplied.
  • JSON dry-run includes the derived write path, change flag, template path, and complete rendered preview.
  • Non-JSON dry-run prints template metadata, warnings, and the rendered text.

A notable edge case is that a no-output, non-dry-run render writes nothing despite calculating a derived path; it emits rendered text to stdout. The derived path is primarily relevant to dry runs and JSON reporting.

Maintenance considerations

Because this file is both a hotspot and the junction between argument parsing, request construction, library calls, filesystem output, and diagnostics, changes should preserve alignment between render and validate flows. In particular, update both paths when changing multi-pass input rules, warning behavior, stdin consumption, output conventions, or observer event timing.
