Overview

catalog.rs is the Application-layer catalog parser and edge connector that consumes reports/catalog/reports.toml and produces validated ReportCatalog and ReportDefinition values for rendering, indexing, scaffolding, template resolution, and the reports command.

The module centralizes the contract for report definitions. It reads TOML from the repository-relative default catalog location, resolves an explicitly supplied catalog path for callers that need alternate input, validates each [[report]] entry, and retains the resolved catalog path alongside the parsed reports.

Validation is intentionally performed during loading, so downstream consumers can operate on typed, internally consistent report definitions rather than repeatedly handling TOML shape errors. A valid report must have:

  • A unique string id.
  • A supported string kind: lint, test, smoke, diagram, state_machine, sql_query, or custom.
  • A string producer.
  • A Boolean required.
  • Normalized relative-path strings for entrypoint and metadata.

Path validation delegates to crate::path_utils::is_normalized_relative_path, preventing report definitions from supplying absolute paths or non-normalized traversal-like paths. The catalog file itself is different: load_report_catalog_from_path accepts either an absolute catalog path or a path relative to repo_root.

CatalogError preserves the distinction between filesystem failures, TOML parsing failures, and semantic validation failures. Its Display implementation includes the affected path for read and parse failures, while validation errors provide report IDs, entry indexes, and field names where applicable.

Public API

All exposed symbols are pub(crate), making this module an internal interface across the sc-compose crate rather than a public library API.

Symbol Purpose
REPORT_CATALOG_RELATIVE_PATH Default catalog location: reports/catalog/reports.toml. Used by loading, scaffolding, and template-related reporting code.
ReportCatalog Parsed catalog result containing the resolved catalog_path and ordered reports collection. Derives Debug, Clone, PartialEq, Eq, and Serialize.
ReportCatalog::load(repo_root) Convenience entry point that loads the default report catalog under repo_root.
ReportDefinition Validated definition of one report: id, kind, producer, required, entrypoint, and metadata. Path fields serialize through the shared path serializer.
CatalogError Error type for catalog loading: Read, Parse, or Invalid. Implements Display and std::error::Error.
load_report_catalog(repo_root) Loads the default reports/catalog/reports.toml catalog.
load_report_catalog_from_path(repo_root, catalog_path) Resolves, reads, parses, and validates a caller-specified catalog path. Useful for tests or alternate repository layouts.

The loader preserves report order from the TOML [[report]] array. It only uses a BTreeSet for duplicate-ID detection; it does not sort the resulting Vec<ReportDefinition>.

Dependencies

  • toml::Value parses the catalog document into a generic TOML tree before semantic validation. This allows the module to issue field-specific errors instead of relying solely on deserialization diagnostics.
  • serde::Serialize enables report catalog data to be emitted by other reporting flows.
  • std::path::{Path, PathBuf} represents repository roots, catalog locations, and report-relative file references.
  • std::collections::BTreeSet tracks IDs encountered while loading and rejects duplicates.
  • std::fmt supports user-facing CatalogError formatting.
  • crate::path_utils::is_normalized_relative_path enforces the safe, portable path contract for report entrypoint and metadata fields.

Callers connect to this module in two main ways:

  1. commands/reports/render.rs calls ReportCatalog::load when rendering reports.
  2. reporting/index.rs calls the same convenience loader while building the report index.

Within the reporting subsystem, scaffolding and template resolution share REPORT_CATALOG_RELATIVE_PATH, keeping generated and discovered catalog locations aligned. load_report_catalog delegates to load_report_catalog_from_path, which calls resolve_catalog_path, then constructs each entry through ReportDefinition::from_value.

Usage Notes

A typical catalog uses a TOML array of tables:

[[report]]
id = "workspace-lint"
kind = "lint"
producer = "cargo"
required = true
entrypoint = "reports/entrypoints/workspace-lint.sh"
metadata = "reports/metadata/workspace-lint.toml"

[[report]]
id = "schema-diagram"
kind = "diagram"
producer = "dbml"
required = false
entrypoint = "reports/entrypoints/schema-diagram.sh"
metadata = "reports/metadata/schema-diagram.toml"

Load the repository-default catalog when working in the normal report layout:

use std::path::Path;

let catalog = ReportCatalog::load(Path::new("/path/to/repository"))?;

for report in &catalog.reports {
    if report.required {
        // Schedule or validate the required report.
    }
}

Use load_report_catalog_from_path when a test fixture or integration flow supplies a different catalog. Relative paths are interpreted relative to repo_root; absolute catalog paths are used unchanged:

let catalog = load_report_catalog_from_path(
    Path::new("/path/to/repository"),
    Path::new("fixtures/reports.toml"),
)?;

Important failure cases to handle or surface:

  • Missing or unreadable catalog files return CatalogError::Read.
  • Syntactically invalid TOML returns CatalogError::Parse.
  • A document without a [[report]] array returns CatalogError::Invalid.
  • Each required field must be present with the correct scalar type; strings such as "true" are not accepted for required.
  • kind comparison is exact and case-sensitive.
  • Duplicate IDs are rejected even when all other fields are valid.
  • entrypoint and metadata must be normalized relative paths. Consumers should join these paths to an appropriate repository/report root; the module deliberately does not resolve them to absolute paths.
  • The error message for an alternate catalog still refers to reports/catalog/reports.toml in several validation contexts, because that constant defines the canonical catalog contract. Callers presenting custom-catalog diagnostics may wish to add their own source context.
