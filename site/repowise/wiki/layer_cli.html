Layer: CLI

I’ll ground the CLI overview in the command modules and their dispatch boundary.

Overview

The CLI layer is the system’s presentation and command-orchestration layer: it turns shell arguments into typed operations, invokes application/composition services, and returns human-readable or JSON results with stable exit codes. It owns the sc-compose executable’s interaction contract, including Clap command definitions, command dispatch, output formatting, diagnostics, and lifecycle observability.

It depends primarily on the Application layer (48 imports) for template composition, report generation, storage, and verification work. Application has one incoming dependency on this layer through the reports command boundary.

Key Components

  • cli.rs defines the command grammar and shared argument structures. It exposes top-level operations including render, resolve, validate, verify, template initialization, workspace setup, template/example packs, observability health, and reports.

  • commands/dispatch.rs is the execution router. It matches each parsed Command and delegates to the corresponding handler while wrapping execution in lifecycle events.

  • commands/compose.rs adapts render, resolve, and validate arguments into sc_composer requests. It handles multi-pass input, custom delimiters, output-target selection, warnings, and terminal/JSON response rendering.

  • commands/verify.rs builds verification requests, applies allowed builtin-variable overrides, compares rendered and deployed output, and reports drift.

  • commands/template_init.rs implements template-init and frontmatter-init: it validates pass-scoped replacements, rewrites template content when requested, and supports dry-run and JSON modes.

  • commands/templates.rs and commands/examples.rs provide list, add, lookup, and render workflows for user-managed template packs and bundled examples.

  • commands/reports/mod.rs is the CLI layer’s edge connector. It defines typed reports subcommands and re-exports their handlers, forming the public bridge used across the CLI/Application boundary.

  • commands/reports/{scaffold,render,publish}.rs adapt report operations—scaffold setup, smoke execution, index/verification, specification rendering, cataloging, finalization, and publish-manifest creation—into CLI output.

  • commands/mod.rs, referenced by the codebase tour as the CLI anchor, aggregates command modules and centralizes shared presentation/error adapters for template-pack failures.

  • command_error.rs converts application and composition failures into CLI-facing diagnostics, recovery hints, and exit codes.

Data Flow

Shell arguments
  → cli.rs parses typed Clap arguments
  → main.rs creates logging/observer context
  → commands/dispatch.rs selects a command handler
  → command adapter builds requests or invokes application services
  → sc-composer / reporting / template-store work executes
  → CommandError or result is normalized
  → terminal text or JSON envelope + process exit code

For composition commands, shared CLI inputs such as root path, resolution mode, variables, variable files, environment prefix, strictness, and output behavior are transformed into composition requests. sc-composer then resolves, validates, renders, or verifies templates; the CLI emits output, diagnostics, and warnings.

For report commands, reports/mod.rs parses the nested subcommand first, then dispatch forwards the typed request to scaffold, rendering, catalog, indexing, verification, finalization, or publishing services. Those services return report metadata and artifact paths, which the CLI presents consistently in text or JSON.

Architecture Notes

  • The CLI is intentionally an adapter, not the composition engine. Template semantics, rendering, validation, and report-domain work remain in the Application layer and sc-composer.

  • Command handlers preserve a consistent interface: Result<i32, CommandError>. This keeps command-specific logic separate from standardized exit behavior.

  • JSON is treated as a first-class output mode. Successful payloads and errors use a common envelope, allowing automation to consume diagnostics without scraping terminal text.

  • Observability surrounds dispatch rather than individual business operations. observe_command records start/end events, elapsed time, success state, output mode, exit code, and diagnostic context while forwarding composition events to the observer.

  • The reports module is the layer’s explicit edge connector. Keep its typed subcommand definitions and handler re-exports stable when evolving cross-layer report workflows.

  • commands/mod.rs is the practical CLI anchor because it exposes the command surface and shared terminal-facing adapters; changes there can affect multiple command families.
