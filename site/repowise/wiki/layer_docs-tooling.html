Overview

Docs & Tooling is the documentation, release-operations, and delivery-support layer that records architectural contracts, guides users and maintainers, and connects repository outputs to documentation sites and package-distribution workflows. It does not implement template composition; it defines, explains, verifies, and operationalizes the behavior owned by sc-composer, sc-compose, and the Python bindings.

This layer serves two audiences:

  • Users, through the GitHub Pages content, installation guidance, examples, and package-manager instructions.
  • Maintainers and release operators, through architecture specifications, ADRs, plans, traceability, release checklists, publishing guidance, and CI/release automation.

The ADR set is especially important because it makes multi-pass behavior concrete:

  • ADR-0002 defines pass-specific brace counts.
  • ADR-0003 and ADR-0004 define stacked-header order and YAML pass authority.
  • ADR-0005 prevents one pass from consuming another pass’s placeholders.
  • ADR-0006 requires longest-match-first substitution in template-init.
  • ADR-0007 keeps verification semantics in sc-composer and CLI presentation in sc-compose.
  • ADR-0008 establishes the committed prototype as the behavioral oracle and preserves ParsedTemplate::frontmatter() compatibility for single-header callers.
  • ADR-0001 limits observability panic-removal changes without prematurely expanding the CLI boundary.

User-facing documentation and installation guidance

For multi-pass composition, the documentation flow is also an implementation contract:

  1. ADRs specify the behavior and identify prototype/multipass/ as the reference implementation.
  2. docs/architecture.md assigns parser, validation, rendering, verification, and workspace helper ownership to sc-composer.
  3. The CLI layer exposes those library capabilities while retaining responsibility for arguments, streams, quiet mode, and exit-code mapping.
  4. Tests and review use the ADRs, prototype, traceability matrix, and sprint material as evidence that the implementation matches the intended behavior.

For release operations:

  1. A maintainer selects a workspace version and follows the checklist.
  2. The release workflow validates manifest and workspace alignment, then runs the release gate.
  3. It builds platform archives containing both bin/sc-compose and share/sc-compose/examples.
  4. Production publishing releases sc-composer before sc-compose, then distributes package-specific artifacts.
  5. docs/WINGET_SETUP.md explains that the first winget manifest is manual; subsequent updates are automated and release verification checks submission success rather than immediate public availability.

Architecture Notes

  • This is a governance and enablement layer, not a runtime dependency. Core crates should not import documentation, workflow, or package-manager concerns.
  • The normative sources are intentionally distinct from public site content. docs/_config.yml excludes architecture, requirements, ADRs, phase plans, sprints, and manifests from the Jekyll build, while docs/index.md links readers to their repository versions.
  • The documented crate boundary is strict: sc-compose → sc-composer, bindings/python → sc-composer, and no reverse dependency or orchestration-runtime dependency in sc-composer.
  • ADR-0007 reinforces the same split for drift checking: sc-composer owns structured VerifyResult behavior, while sc-compose owns command-line interaction.
  • The release documentation makes artifact layout part of the product contract: package builds and GitHub Release archives must preserve bundled examples, whereas cargo install ships only the binary and relies on SC_COMPOSE_DATA_DIR for an external examples root.
  • There is a deployment configuration boundary worth keeping visible: docs/_config.yml describes a Jekyll site rooted in docs, while .github/workflows/pages.yml currently uploads site. Any Pages deployment change should keep those two sources aligned so the configured content is the content actually published.
