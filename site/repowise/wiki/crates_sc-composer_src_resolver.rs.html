File: crates/sc-composer/src/resolver.rs

Overview

resolver.rs is the Application-layer resolver for compose requests — it consumes ComposeRequest values and produces canonical ResolveResult template paths with search traces, confinement enforcement, ambiguity detection, and optional observer events.

It handles two resolution modes:

  • File mode: resolves an explicitly supplied template path relative to the request root when needed, canonicalizes it, and rejects paths outside the configured confinement roots.
  • Profile mode: searches runtime-specific and shared agent, command, or skill directories for a named profile; returns one concrete template path only when exactly one distinct candidate matches.

The resolver is called by the composition flow through composer.rs, while frontmatter_init.rs, lib.rs, and the CLI can use its public functions to resolve templates independently. It does not render templates or parse CLI input; it turns selection intent into a safe, traceable filesystem path.

Public API

resolve_template_path

pub fn resolve_template_path(
    request: &ComposeRequest,
) -> Result<ResolveResult, ComposeError>

Primary entry point for resolving the template targeted by a compose request.

  • For ComposeMode::Profile, delegates to profile resolution using the request root, profile kind and name, optional runtime, and ResolverPolicy.
  • For ComposeMode::File, canonicalizes the requested path and ensures it remains under the request root or an allowed additional root.
  • Returns a ResolveResult containing:
  • resolved_path: the canonical selected template.
  • attempted_paths: one path for file mode, or every unique profile probe attempted.
  • ambiguity_candidates: currently empty on successful resolution.

Use this from the normal composition pipeline when callers do not need profile-resolution observer callbacks.

resolve_profile

pub fn resolve_profile(
    request: &ComposeRequest,
) -> Result<ResolveResult, ComposeError>

Resolves only profile-mode requests. It installs NoopObserver and delegates to resolve_profile_with_observer.

Passing a file-mode request returns ComposeError::Config with DiagnosticCode::ErrConfigMode.

resolve_profile_with_observer

pub fn resolve_profile_with_observer(
    request: &ComposeRequest,
    observer: &mut dyn CompositionObserver,
) -> Result<ResolveResult, ComposeError>

Profile resolver variant that emits tracing callbacks.

For a profile request, it:

  1. Emits on_resolve_attempt with a "{kind:?}:{name}" template identifier.
  2. Performs filesystem lookup.
  3. Emits on_resolve_outcome for successful and resolver-specific failed lookups.

A successful outcome includes the canonical path and all attempted paths. A ComposeError::Resolve failure includes the attempted paths and diagnostic code. Non-resolution errors are returned without an outcome callback.

This is the appropriate API for callers that expose diagnostics, progress reporting, or audit traces.

Resolution behavior

Without policy overrides, runtime-aware lookup uses these runtime orders when no runtime is specified:

  1. Claude
  2. Codex
  3. Gemini
  4. Opencode

For each runtime and profile kind, the resolver searches runtime-specific paths followed by shared fallback paths. For example, Codex agent lookup considers:

.codex/agents
.agents/agents
.claude/agents

Filename probes are profile-kind specific:

Profile kind Default probe order
Agent / Command <name>.md.j2, <name>.md, <name>.j2
Skill <name>/SKILL.md.j2, <name>/SKILL.md, <name>/SKILL.j2

ResolverPolicy can replace both directory selection and filename probe lists. Custom relative directories are joined to the request root; custom absolute directories are used as supplied.

Errors and edge cases

  • Missing explicit file or profile candidate: ErrResolveNotFound.
  • Explicit file outside all configured roots: ErrResolveNotFound.
  • More than one distinct profile file matches: ErrResolveAmbiguous.
  • Calling profile-only APIs in file mode: ErrConfigMode.
  • A candidate that exists but cannot be canonicalized becomes a resolver error with the original I/O error attached.

The resolver deduplicates attempted paths and canonical matched files with BTreeSet. This prevents duplicate trace entries when runtime fallback chains overlap and prevents the same file from becoming ambiguous merely because it is reachable through multiple search paths.

Dependencies

Internal modules

  • types
  • Supplies request modes, profile identifiers, runtime and profile kinds, confinement roots, resolver policy, and the ResolveResult output type.
  • error
  • Supplies ComposeError, ConfigError, and ResolveError, including diagnostic codes and source-error attachment.
  • diagnostics
  • Supplies DiagnosticCode values used to classify mode, missing-path, and ambiguity failures.
  • observer
  • Supplies CompositionObserver, NoopObserver, ResolveAttemptEvent, and ResolveOutcomeEvent.

Standard library

  • std::fs::canonicalize validates filesystem existence and resolves the final physical path.
  • Path and PathBuf build root-relative and runtime-specific lookup paths.
  • BTreeSet preserves unique attempted paths and matches deterministically.

Call relationships

composer.rs calls resolve_template_path during composition, then passes the resolved template into later loading and rendering stages. resolve_template_path dispatches to either resolve_profile_impl or canonicalize_with_roots.

resolve_profile is a convenience wrapper over resolve_profile_with_observer; both eventually use the same private resolution implementation, so observer-enabled and observer-free profile lookup follow identical search semantics.

Usage Notes

Resolve an explicit template safely

Construct a file-mode request with a root and, if necessary, additional allowed roots:

let request = ComposeRequest {
    runtime: None,
    mode: ComposeMode::File {
        template_path: "templates/release.md.j2".into(),
    },
    root: ConfiningRoot::new(project_root)?,
    policy: ComposePolicy::default(),
    // Populate variables and optional prompt fields as required.
    ..request_defaults
};

let result = resolve_template_path(&request)?;
let template = result.resolved_path;

Relative paths are interpreted beneath request.root. Absolute paths are permitted only when their canonical form begins with the canonical request root or one of policy.allowed_roots.

A common pitfall is assuming lexical path checks are enough. They are not: canonicalization handles .. segments and symlink traversal before applying confinement.

Resolve a runtime-specific profile

let request = ComposeRequest {
    runtime: Some(RuntimeKind::Codex),
    mode: ComposeMode::Profile {
        kind: ProfileKind::Skill,
        name: ProfileName::new("release-notes")?,
    },
    root: ConfiningRoot::new(project_root)?,
    policy: ComposePolicy::default(),
    ..request_defaults
};

let result = resolve_profile(&request)?;

For this request, lookup checks Codex skill locations, then shared fallback locations, and probes templated skill files before non-templated variants.

Resolve with an observer

let mut observer = MyCompositionObserver::default();
let result = resolve_profile_with_observer(&request, &mut observer)?;

Observers receive one attempt event before lookup and one outcome event for success or resolver failures. Use attempted_paths in the outcome to explain where the resolver looked, especially when a profile is missing.

Handle omitted-runtime ambiguity

When request.runtime is None, the resolver searches all supported runtimes. This is useful for portable profile discovery, but duplicate profiles across runtime directories are intentionally errors rather than priority-selected matches.

match resolve_profile(&request) {
    Ok(result) => use_template(result.resolved_path),
    Err(ComposeError::Resolve(error))
        if error.code() == DiagnosticCode::ErrResolveAmbiguous =>
    {
        // Ask the caller to choose RuntimeKind explicitly.
    }
    Err(error) => return Err(error),
}

Set an explicit RuntimeKind whenever the project intentionally contains same-named profiles for multiple runtimes.

Customize lookup policy carefully

ResolverPolicy::candidate_directories and ResolverPolicy::filename_probes replace the defaults rather than extend them. Supplying either non-empty list means the built-in runtime directory matrix or filename extension ordering is no longer used for that dimension.

Custom probe values are joined directly to candidate directories. Keep them relative and avoid user-controlled traversal segments unless the surrounding application validates policy configuration.
