Overview

template_store.rs is the Application-layer edge-connector and filesystem-backed template-pack resolver, producing TemplateMeta inventories and render-ready TemplatePack values for CLI commands and render_request. It separates bundled examples from user-managed templates while presenting both through a common TemplateStore interface.

The module has two storage modes:

  • StoreKind::Examples reads bundled, flat *.j2 files from <data-dir>/examples.
  • StoreKind::Templates reads user template-pack directories from the platform data directory or SC_COMPOSE_TEMPLATE_DIR.

It is consumed by commands/examples.rs and commands/templates.rs for list, render, and add commands, and by render_request.rs through TemplatePack. A resolved pack supplies the confinement root, exactly one render entrypoint, and validated manifest defaults used to construct a ComposeRequest.

Template discovery is intentionally strict:

  • Example names are derived from root-level *.j2 filenames, with a possible secondary extension removed (example.md.j2 becomes example).
  • A user template is a directory whose name is the pack name.
  • Rendering a user pack requires exactly one root-level *.j2 file.
  • Nested templates and assets may be copied into a pack but cannot be its render entrypoint.
  • template.json, when present, supplies listing metadata and input defaults.

Public API

All interfaces are pub(crate): they form the CLI crate’s internal application API rather than a public library contract.

Item Purpose
TemplateStore::examples() -> Result<TemplateStore> Creates a store rooted at data_dir()/examples for bundled examples.
TemplateStore::templates() -> Result<TemplateStore> Creates a store rooted at user_templates_dir() for user packs.
TemplateStore::ensure_templates_root() For a template store, creates the root directory and writes README.md if absent. It is a no-op for an example store.
TemplateStore::list() -> Result<Vec<TemplateMeta>> Lists packs for the active store kind, sorted lexicographically by name. A missing root yields an empty list.
TemplateStore::get_example(name) Resolves one bundled example into a TemplatePack, or None if absent. Fails if multiple files map to the same logical example name.
TemplateStore::get_template(name) Resolves a user pack into a validated, renderable TemplatePack, or None if the named directory does not exist. Separates parse failures from non-renderable layout failures.
TemplateStore::add(source, requested_name) Imports a file or directory as a new user template pack. Refuses to overwrite an existing destination.
data_dir() Resolves bundled data location from SC_COMPOSE_DATA_DIR, otherwise from ../share/sc-compose relative to the executable directory.
user_templates_dir() Resolves user template root from SC_COMPOSE_TEMPLATE_DIR, otherwise from the platform user-data directory plus sc-compose/templates.

Data types

  • TemplateMeta is a list-facing record containing name, filesystem path, and optional manifest description and version.
  • TemplatePack is the rendering handoff. root is the pack directory, template_path is relative to that root, and input_defaults contains validated manifest defaults keyed by VariableName.
  • TemplateAddResult reports the imported pack’s effective name, canonical source, destination, and whether state changed. Successful additions always set changed to true.
  • AddError::AlreadyExists preserves the destination path so CLI callers can produce a dedicated conflict diagnostic. Other failures are wrapped as AddError::Other.
  • GetTemplateError::Parse covers manifest, filesystem enumeration, and default-validation errors. GetTemplateError::NotRenderable identifies an existing pack that lacks a unique root-level template entrypoint.

Methods assert their intended store kind. Calling get_example on a template store, or get_template/add on an example store, is a programmer error and panics.

Dependencies

  • std::fs, Path, and PathBuf provide all persistence, discovery, copying, and path construction. No database or external storage abstraction is involved.
  • anyhow adds context to filesystem, manifest, and environment-resolution errors; specialized enums preserve CLI-relevant error categories.
  • serde::Deserialize and serde_json parse the optional template.json manifest.
  • sc_composer::{VariableName, InputValue, validate_input_value} keeps manifest defaults consistent with the composer’s accepted variable-name and JSON-value model.
  • BTreeMap provides deterministic storage for discovered example collisions and validated default values.

Usage Notes

Bundled examples

Examples are flat files under the resolved data directory:

<data-dir>/
└── examples/
    ├── greeting.j2
    └── report.md.j2

TemplateStore::list() reports the names greeting and report. get_example("report") returns a pack rooted at <data-dir>/examples with template_path set to report.md.j2.

Only immediate child files with a case-insensitive .j2 extension are considered. Directories and non-template files are ignored. Name derivation can collide: report.j2 and report.md.j2 both derive report, causing both listing and retrieval to fail with an ambiguity error rather than selecting one arbitrarily.

User template packs

A renderable user pack has one directory and one root-level entrypoint:

<template-root>/
└── invoice/
    ├── invoice.md.j2
    ├── template.json
    └── assets/
        └── logo.svg

A suitable template.json is:

{
  "description": "Markdown invoice",
  "version": "1.0.0",
  "input_defaults": {
    "currency": "USD",
    "paid": false
  }
}

When get_template("invoice") is called, the module:

  1. Finds <template-root>/invoice only if it is a directory.
  2. Reads and deserializes template.json when it exists.
  3. Validates each input_defaults key as a composer VariableName.
  4. Validates each default value with sc_composer::validate_input_value.
  5. Scans only the pack root for *.j2 files.
  6. Returns a TemplatePack if exactly one entrypoint exists.

build_named_request then uses TemplatePack.root as a ConfiningRoot, renders the relative template_path, and passes input_defaults as composition defaults.

A pack can be listed even when it is not renderable: listing only requires a directory and a parseable manifest. Rendering subsequently reports NotRenderable if there are zero or multiple root-level templates. This distinction lets templates list surface installed packs while templates <name> gives a layout-specific error.

Adding template packs

TemplateStore::add supports either a source file or a source directory:

sc-compose templates add ./welcome.md.j2 welcome
sc-compose templates add ./invoice-pack invoice

For a file source, the store creates <template-root>/<name>/ and copies the file into it. For a directory source, it recursively copies every file and nested directory, preserving the source tree. The source is canonicalized first, and the resulting TemplateAddResult.source is therefore absolute.

Without an explicit name, a directory uses its basename. A .j2 file uses the same logical-name rule as examples, so welcome.md.j2 defaults to welcome; other files use their stem. The requested name is joined directly beneath the template root, so CLI validation should constrain names appropriately before calling this API.

The operation does not merge or overwrite packs. If the destination already exists, it returns AddError::AlreadyExists; callers should present this as a conflict and leave the existing pack untouched. A copy failure can leave a partially created destination, so retrying may require inspecting or removing that incomplete pack manually.

Location overrides and portability

SC_COMPOSE_DATA_DIR overrides the bundled data root, and SC_COMPOSE_TEMPLATE_DIR overrides the user template root. Relative override values are converted to absolute paths using the process’s current working directory, not the executable location.

Without overrides, user template locations are:

Platform Base directory
Windows APPDATA, falling back to LOCALAPPDATA
macOS $HOME/Library/Application Support
Other platforms XDG_DATA_HOME, falling back to $HOME/.local/share

The final user root is always <base>/sc-compose/templates. ensure_templates_root creates it lazily and writes a short README only when one does not already exist.
