Overview

composer.rs is the Application-layer composition orchestrator that consumes a ComposeRequest and produces a ComposeResult by resolving templates, expanding includes, validating variables, rendering one or more passes, and assembling optional output blocks.

The public compose path is the library’s end-to-end entry point, used by the crate facade, CLI request handling, integration tests, and language bindings. It sequences the workflow in a fixed order:

  1. Resolve the requested profile or file path.
  2. Expand template includes under the configured confining root and policy.
  3. Validate the expanded template and construct variable state.
  4. Render either a single template or ordered multi-pass template.
  5. Append the optional guidance block and user prompt.
  6. Return rendered text, resolved files, resolution metadata, variable provenance, and warnings.

This is a high-activity, high-complexity hotspot. Changes can affect resolution behavior, include safety, validation precedence, render semantics, observer telemetry, and final output formatting; preserve the sequencing and error boundaries when modifying it.

Public API

compose

pub fn compose(request: &ComposeRequest) -> Result<ComposeResult, ComposeError>

Runs composition without requiring instrumentation. It installs NoopObserver and delegates to compose_with_observer, ensuring the unobserved and observed paths share the same behavior.

Use this for ordinary library callers that only need the completed result or an error.

compose_with_observer

pub fn compose_with_observer(
    request: &ComposeRequest,
    observer: &mut dyn CompositionObserver,
) -> Result<ComposeResult, ComposeError>

Runs the same composition pipeline while emitting lifecycle events:

  • on_resolve_attempt before resolution.
  • on_resolve_outcome after success or resolution failure.
  • on_include_outcome after include expansion or include failure.
  • on_validation_outcome after validation.
  • on_pass_start and on_pass_end around each multi-pass render.
  • on_render_outcome after successful rendering or rendering failure.

Resolution and include failures notify the observer before returning. Validation errors are emitted as an outcome and then converted into a fatal ComposeError. Render failures emit a failed render outcome with no byte count.

render_all

pub fn render_all(
    parsed: &ParsedTemplate,
    contexts: &[(u8, BTreeMap<VariableName, InputValue>)],
) -> Result<String, ComposeError>

Renders a parsed multi-pass template without instrumentation. The context list must have exactly one entry per parsed pass, in the same pass-number order.

For each pass, the function:

  • derives delimiters from the pass number ({{…}} for pass 1, {{{…}}} for pass 2, and so on);
  • protects expressions using the next-higher brace width;
  • merges frontmatter defaults with the supplied pass context, with supplied values taking precedence;
  • renders the body using a delimiter-configured Renderer.

A mismatched context count or pass number is reported as ErrConfigParse.

protect_higher_braces

pub fn protect_higher_braces(text: &str, brace_count: usize) -> String

Wraps complete expressions using one additional brace level in MiniJinja raw blocks. This prevents a lower render pass from interpreting syntax reserved for a later pass.

It leaves text unchanged when no higher-brace opening delimiter exists. If a higher-brace opening delimiter has no matching closing delimiter, it preserves the remaining input rather than attempting partial protection.

Usage Notes

A standard caller provides a confined root, mode, variable sources, optional trailing blocks, and policy:

use std::collections::BTreeMap;
use std::path::PathBuf;

use sc_composer::{
    compose, ComposeMode, ComposePolicy, ComposeRequest, ConfiningRoot,
};

let request = ComposeRequest {
    runtime: None,
    mode: ComposeMode::File {
        template_path: PathBuf::from("profiles/report.md.j2"),
    },
    root: ConfiningRoot::new("./templates")?,
    vars_input: BTreeMap::new(),
    vars_env: BTreeMap::new(),
    vars_defaults: BTreeMap::new(),
    guidance_block: Some("Follow the repository conventions.".to_owned()),
    user_prompt: Some("Generate the release report.".to_owned()),
    policy: ComposePolicy::default(),
};

let result = compose(&request)?;
println!("{}", result.rendered_text);

ComposeResult retains more than the rendered string. Callers that need explainability should inspect:

  • resolved_files to identify the root template and included files;
  • resolve_result to inspect the successful resolution result;
  • variable_sources to determine whether a value came from explicit input, environment, defaults, frontmatter, or built-ins;
  • warnings for non-fatal validation findings.

For progress reporting, diagnostics, or UI integration, use compose_with_observer. Observers receive failure events before the corresponding error is returned, so consumers can report the failed pipeline phase without parsing error text.

Multi-pass behavior requires special care. Context pass numbers must align with the template frontmatter order, and higher-brace expressions are deliberately preserved until their own pass. Do not replace protect_higher_braces with a simple repeated render: doing so would allow an earlier pass to consume syntax intended for a later one.

Variable precedence is established during validation and reinforced during rendering. In a multi-pass template, frontmatter defaults are first collected per pass, the flattened validated context is merged, and configured pass defaults are merged last when explicit pass configurations are supplied. This supports explicit inputs overriding weaker sources while keeping per-pass defaults available.

The single-pass path renders the expanded text directly with the fully built render context. The multi-pass path instead derives delimiters from each frontmatter pass number. Both paths emit one final successful RenderOutcomeEvent containing the byte length of the rendered template body before guidance and prompt blocks are appended.
