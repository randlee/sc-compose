File: crates/sc-composer/src/lib.rs

Overview

sc-composer’s lib.rs is the Application-layer public entry point and edge connector for the composition subsystem, exposing rendering, composition, resolution, validation, verification, diagnostics, and workspace-initialization APIs to the CLI and Python bindings. It is central to the dependency graph because downstream callers import this single crate surface instead of reaching into individual implementation modules.

The file establishes the crate’s public contract in three ways:

  • Declares the subsystem modules that implement composition behavior.
  • Re-exports selected functions, types, traits, and constants as a stable flat API.
  • Hosts focused regression tests for rendering errors and frontmatter normalization.

Most behavior is implemented in sibling modules; this file intentionally contains little runtime logic. Its architectural value is API curation: it determines what consumers of sc_composer may depend on without coupling them to internal module paths such as composer, renderer, or resolver.

The crate-level #![deny(missing_docs)] makes undocumented public items compile-time errors. This is particularly important for this boundary because it is consumed by the sc-compose CLI, integration tests, and Python bindings.

Public API

Composition and rendering

  • compose, compose_with_observer, and render_all provide end-to-end template composition.
  • protect_higher_braces supports handling template syntax that uses deeper brace nesting.
  • Renderer, render_template, and render_loaded_template expose direct rendering operations.
  • LoadedTemplateRequest, NamedTemplateAsset, and RenderedArtifact model loaded-template rendering inputs and outputs.

Consumers that need lifecycle visibility should use the *_with_observer variants rather than duplicating orchestration around the base operations.

Template preparation

  • parse_template_document parses a template document into ParsedTemplate and optional Frontmatter.
  • expand_includes recursively expands include directives and returns ExpandedTemplate.
  • frontmatter_init initializes frontmatter-related template state.
  • init_workspace and read_optional_text_file support workspace bootstrap and optional configuration loading.
  • to_forward_slash provides normalized slash-separated path formatting.

Frontmatter defaults support scalar, object, array, and array-of-object values. input_defaults is accepted as an alias for defaults; if both sections are present, the parsed defaults use input_defaults values and emit WarnValConflictingDefaultSections.

Resolution, validation, and verification

  • resolve_profile, resolve_profile_with_observer, and resolve_template_path resolve runtime-aware profiles and template paths.
  • validate and validate_with_observer provide public validation entry points.
  • verify and verify_with_observer provide drift-verification entry points.
  • discover_tokens, discover_tokens_with_brace_count, and discover_all_pass_tokens expose variable-token discovery helpers.
  • BUILTIN_VARIABLE_NAMES identifies variables supplied by the system rather than template input.

The corresponding model types include ComposeRequest, ComposeResult, ComposePolicy, ResolverPolicy, ValidationReport, VerifyResult, ProfileName, VariableName, and InputValue.

Errors and diagnostics

The crate exports canonical, crate-owned error types:

  • ComposeError
  • ConfigError
  • IncludeError
  • RenderError
  • ResolveError
  • ValidationError

It also exports recovery metadata through RecoveryHint and RecoveryHintKind.

Diagnostics are exposed through Diagnostic, DiagnosticCode, DiagnosticEnvelope, DiagnosticSeverity, and DIAGNOSTIC_SCHEMA_VERSION. This lets outer layers—especially CLI JSON output and language bindings—serialize structured failure and warning information without depending on internal diagnostics implementation details.

Observation API

CompositionObserver, ObservationSink, and NoopObserver define the observability boundary. Event payload types cover composition passes, resolution attempts and outcomes, include outcomes, rendering outcomes, validation, and verification:

  • PassStartEvent / PassEndEvent
  • ResolveAttemptEvent / ResolveOutcomeEvent
  • IncludeOutcomeEvent
  • RenderOutcomeEvent
  • ValidationOutcomeEvent
  • VerifyStartEvent / VerifyEndEvent
  • ObservationEvent

The CLI’s composition command uses this surface to report progress and outcomes while keeping observer implementation outside the pure composition library.

Dependencies

lib.rs depends only on crate-local modules and standard test dependencies:

Area Modules Role
Composition pipeline composer, include, renderer, resolver Compose templates, expand includes, render content, and locate profiles/templates.
Data and parsing types, frontmatter, frontmatter_init Define request/result models and parse or initialize frontmatter.
Quality and reporting validation, validate, verify, diagnostics, error Discover variables, validate inputs, verify drift, and return structured failures.
Integration support observer, init_workspace, path_utils Emit lifecycle events, initialize workspaces, and normalize paths.

path_utils is deliberately private (mod path_utils), but to_forward_slash is re-exported. This permits consumers to use the supported path-normalization operation while preserving freedom to reorganize its implementation.

The primary dependents are:

  • crates/sc-compose, which adapts library operations into CLI commands, JSON output, reporting, and command-specific error handling.
  • bindings/python, which converts exported types and errors into Python-facing equivalents.
  • crates/sc-composer/tests/integration.rs, which validates the public library surface rather than private implementation details.

This dependency pattern preserves the intended direction: outer interfaces depend on sc-composer; the composition library does not import CLI or binding code.

Usage Notes

Use the root re-exports for application code. This keeps imports concise and avoids tying callers to internal file layout.

use sc_composer::{ComposeRequest, compose};

let request = ComposeRequest::default();
let result = compose(request)?;

For a simple inline rendering operation, use render_template with JSON-compatible input:

use sc_composer::render_template;
use serde_json::json;

let output = render_template(
    "Hello {{ name }}",
    json!({ "name": "world" }),
)?;

assert_eq!(output, "Hello world");

For document templates, parse frontmatter before rendering or validation:

use sc_composer::parse_template_document;

let parsed = parse_template_document(
    "---\nrequired_variables:\n  - name\n---\nHello {{ name }}\n",
)?;

let frontmatter = parsed.frontmatter();

When a template provides both defaults and the legacy-compatible input_defaults, treat the resulting diagnostic as actionable. The parser accepts both forms, but conflicting values are normalized toward input_defaults, which can silently change expected input values if diagnostics are ignored.

Use observer-aware entry points for user-facing workflows:

use sc_composer::{compose_with_observer, CompositionObserver};

// Implement CompositionObserver in the CLI, UI, or binding layer,
// then pass it to compose_with_observer.

Avoid importing private implementation paths such as sc_composer::path_utils; only the root-level re-export is part of the supported contract. Likewise, prefer exported error families and diagnostics when translating failures at boundaries, so source errors, backtraces, recovery hints, and stable diagnostic codes remain available.

The unit tests in this file protect several contract-level edge cases:

  • Invalid template syntax produces a RenderError that retains its source error and backtrace.
  • Omitted frontmatter defaults and metadata normalize to empty maps.
  • Default values preserve structured JSON-like objects and arrays.
  • input_defaults remains supported as an alias.
  • Conflicting default sections emit a warning diagnostic.
