Overview

include.rs is the Application-layer include-expansion resolver that consumes a root template plus confinement policy and produces expanded template text, provenance metadata, parsed frontmatter, and include chains. It recursively replaces standalone @<path> directives, validates every target against the primary and explicitly allowed roots, and turns operational failures into structured ComposeError::Include diagnostics.

The module is called by the end-to-end composer after template resolution and before validation/rendering. Validation also consumes its ExpandedTemplate output directly, so this module is the boundary where a multi-file template graph becomes a single renderable body while retaining file-level metadata.

Expansion is depth-first and deterministic:

  1. Canonicalize and confinement-check the initial template.
  2. Read and parse its frontmatter/body.
  3. Scan the body line by line.
  4. Replace each directive line with the recursively expanded included file.
  5. Return the final text plus traversal and provenance data.

Public API

expand_includes

pub fn expand_includes(
    template_path: impl AsRef<Path>,
    root: &ConfiningRoot,
    policy: &ComposePolicy,
) -> Result<ExpandedTemplate, ComposeError>

Expands a template file and every reachable include directive.

Inputs:

  • template_path — the initial template path. It is canonicalized and must be inside root or policy.allowed_roots.
  • root — the canonical primary confinement root.
  • policy — supplies max_include_depth and additional permitted allowed_roots.

Returns ComposeError when:

  • a target cannot be read (ErrIncludeNotFound);
  • a target is outside the permitted roots (ErrIncludeEscape);
  • recursion exceeds max_include_depth (ErrIncludeDepth);
  • the active include stack revisits a file (ErrIncludeCycle);
  • frontmatter parsing fails; configuration parsing errors are converted into the include error family.

ExpandedTemplate

pub struct ExpandedTemplate {
    pub text: String,
    pub resolved_files: Vec<PathBuf>,
    pub frontmatters: Vec<(PathBuf, Vec<Frontmatter>)>,
    pub include_chains: BTreeMap<PathBuf, Vec<PathBuf>>,
}

The include engine returns both expanded content and the information later pipeline stages need.

Field Meaning Ordering / duplication behavior
text Concatenated template body after directive replacement. Follows source order and depth-first expansion.
resolved_files Canonical files encountered during expansion. First-seen order; each canonical path appears once.
frontmatters Parsed frontmatter passes for each file read. Appended whenever a file is expanded, so repeated non-cyclic includes can produce repeated entries.
include_chains The root-to-file path chain for each resolved file. Recorded only on first encounter; keys are canonical paths and are deterministically ordered by BTreeMap.

ExpandedTemplate derives Clone, Debug, Default, and PartialEq, making it suitable for inspection, testing, and pipeline handoff.

Dependencies

  • types::{ComposePolicy, ConfiningRoot, IncludeDepth} supplies the confinement and recursion policy. ConfiningRoot::new canonicalizes root paths before they reach this module.
  • frontmatter::{parse_template_document, Frontmatter} splits every included file into frontmatter passes and body text. Include directives are evaluated only from the parsed body, not from frontmatter.
  • error::{ComposeError, IncludeError} and DiagnosticCode provide stable, structured failure reporting and preserve the active include chain.
  • std::fs provides file reads and filesystem canonicalization.
  • BTreeSet tracks first-seen canonical paths; BTreeMap stores reproducibly ordered include-chain metadata.
  • composer.rs invokes expand_includes between template resolution and validation/rendering. validation.rs uses the resulting text and frontmatter provenance to analyze the fully composed template.
  • lib.rs re-exports ExpandedTemplate and expand_includes as public crate API.

Usage Notes

Directive syntax

An include directive must occupy its own logical line after trimming whitespace:

@<partials/header.md>

Leading and trailing whitespace around the entire directive is accepted:

    @<partials/header.md>

The implementation does not recognize inline directives:

Intro @<partials/header.md>

That line remains literal text. The directive target is not additionally trimmed, so avoid padding the path inside < and >.

Resolution order

For @<target>, the engine tries:

  1. A path relative to the including file’s parent directory.
  2. A path relative to the primary root if the first attempt does not produce an accepted canonical path.

This lets nested partials use sibling-relative includes while allowing root-relative shared paths.

For example:

templates/
├── report.md.j2
├── shared/footer.md
└── sections/
    ├── summary.md
    └── details.md

report.md.j2:

@<sections/summary.md>
@<shared/footer.md>

sections/summary.md:

Summary
@<details.md>

Calling expand_includes on report.md.j2 produces body text in this order:

Summary
...contents of details.md...
...contents of shared/footer.md...

and records first-seen files as report.md.j2, sections/summary.md, sections/details.md, then shared/footer.md.

Confinement and symlink safety

Every existing candidate is canonicalized before its location is accepted. Consequently, a symlink located inside the template tree but resolving outside it is rejected. Permitted locations are:

  • the primary root;
  • any canonical root listed in ComposePolicy::allowed_roots.

For a nonexistent path, canonicalization cannot expose its final filesystem location. The module therefore lexically normalizes . and .. components before deciding whether the request is an escape. This deliberately reports a nonexistent ../outside.md as an escape rather than misleadingly reporting it as missing.

Cycles and depth

Cycle detection uses the current recursion stack, not the global visited set. A file may be included more than once in separate branches and its contents will be expanded each time; only re-entering a file already on the active chain is a cycle.

resolved_files and include_chains are first-seen metadata, while the final text preserves every valid inclusion occurrence. The root begins at depth 0; each nested include increments depth, and the engine errors once the current depth is greater than policy.max_include_depth.

The default policy allows depth 32. Configure a lower limit when composing untrusted or unusually broad include trees:

use sc_composer::{ComposePolicy, ConfiningRoot, IncludeDepth, expand_includes};

let root = ConfiningRoot::new("templates")?;
let policy = ComposePolicy {
    max_include_depth: IncludeDepth::new(8),
    ..ComposePolicy::default()
};

let expanded = expand_includes("templates/report.md.j2", &root, &policy)?;

Frontmatter behavior

Every file is parsed with parse_template_document before body expansion. Its frontmatter passes are retained in ExpandedTemplate::frontmatters; the body alone contributes to text. The composer subsequently identifies the root template’s saved frontmatter to construct the render pipeline, while validation can inspect frontmatter from included files for warnings and declarations.

Error handling

Consumers that need include-specific diagnostics should match the error family and inspect the stable code and chain:

match expand_includes(template_path, &root, &policy) {
    Ok(expanded) => {
        println!("{}", expanded.text);
    }
    Err(ComposeError::Include(error)) => {
        eprintln!("{}: {}", error.code().as_str(), error.message());
        for path in error.include_chain() {
            eprintln!("  included from {}", path.display());
        }
    }
    Err(other) => return Err(other),
}

Do not treat resolved_files as a complete expansion event log: it intentionally de-duplicates paths. Use the expanded text for occurrence-sensitive behavior, and use include_chains for first-discovery provenance.
