File: crates/sc-composer/src/observer.rs

Overview

observer.rs is the Application-layer edge connector for composition telemetry: it defines the event payloads consumed by embedded hosts and the CLI, plus observer interfaces that receive lifecycle notifications from resolution, include expansion, validation, verification, and rendering.

The module is the public telemetry boundary of sc-composer. Core composition code emits typed, serializable events without depending on CLI presentation or host-specific logging; cross-layer consumers implement one or both traits to collect, display, or forward those events.

ObservationEvent is a tagged event stream covering the full composition lifecycle:

  • Pass boundaries: PassStart, PassEnd
  • Verification boundaries: VerifyStart, VerifyEnd
  • Resolution: ResolveAttempt, ResolveOutcome
  • Include expansion: IncludeExpandOutcome
  • Validation: ValidationOutcome
  • Rendering: RenderOutcome

Every payload derives Serialize, allowing a consumer to turn the event stream into structured output such as JSON without introducing serialization logic into the composer pipeline.

The module exposes two complementary integration styles:

  • CompositionObserver provides named callback hooks. Each method has a default no-op implementation, so consumers override only the lifecycle events they need.
  • ObservationSink provides a single emit(&ObservationEvent) entry point for consumers that prefer a uniform event stream.

NoopObserver implements both traits and is the default safe substitute when no host observer is injected. This keeps normal composition functional and makes telemetry opt-in rather than a required runtime dependency.

Public API

ObservationEvent

ObservationEvent is the unified, serializable envelope for telemetry. Consumers matching on this enum can process all lifecycle notifications through one dispatch point.

Variant Payload Meaning
PassStart PassStartEvent A render pass is about to begin.
PassEnd PassEndEvent A render pass has completed.
VerifyStart VerifyStartEvent Verification has begun.
VerifyEnd VerifyEndEvent Verification has completed.
ResolveAttempt ResolveAttemptEvent Resolution has started for a template or profile identifier.
ResolveOutcome ResolveOutcomeEvent Resolution succeeded or failed.
IncludeExpandOutcome IncludeOutcomeEvent Include expansion succeeded or failed.
ValidationOutcome ValidationOutcomeEvent Validation completed with warnings and/or errors.
RenderOutcome RenderOutcomeEvent Rendering succeeded or failed.

It derives Clone, Debug, PartialEq, and Serialize, making it suitable for capturing in tests, diagnostic output, and structured telemetry pipelines.

ObservationSink

pub trait ObservationSink {
    fn emit(&mut self, event: &ObservationEvent);
}

Implement this trait when the consumer wants a single event-stream interface. The event is borrowed, so sinks should copy or serialize data if they need to retain it after the callback returns.

The documentation explicitly distinguishes this method from deprecated downstream logger APIs that may also use the name emit.

CompositionObserver

CompositionObserver is a callback-oriented extension point. All callback methods are optional and default to no-ops:

pub trait CompositionObserver {
    fn on_pass_start(&mut self, event: &PassStartEvent) {}
    fn on_pass_end(&mut self, event: &PassEndEvent) {}
    fn on_verify_start(&mut self, event: &VerifyStartEvent) {}
    fn on_verify_end(&mut self, event: &VerifyEndEvent) {}
    fn on_resolve_attempt(&mut self, event: &ResolveAttemptEvent) {}
    fn on_resolve_outcome(&mut self, event: &ResolveOutcomeEvent) {}
    fn on_include_outcome(&mut self, event: &IncludeOutcomeEvent) {}
    fn on_validation_outcome(&mut self, event: &ValidationOutcomeEvent) {}
    fn on_render_outcome(&mut self, event: &RenderOutcomeEvent) {}
}

Use this interface when a consumer benefits from type-specific handlers—for example, printing resolution failures differently from validation diagnostics.

The composer invokes this trait from its observed composition paths, while CLI command paths and integration tests supply implementations such as CliObserver and capturing observers.

NoopObserver

NoopObserver is a zero-sized, Default no-op implementation of both CompositionObserver and ObservationSink.

Use it when generic code requires an observer but no telemetry output is desired. Its presence guarantees that observer callbacks do not change composition results or introduce side effects.

Event payloads

Pass and verification events

  • PassStartEvent { pub pass_number: u8 }
  • PassEndEvent { pub pass_number: u8 }
  • VerifyStartEvent
  • VerifyEndEvent

PassStartEvent::new(pass_number) and PassEndEvent::new(pass_number) construct pass-boundary events. The u8 pass number should be treated as an ordinal supplied by the composition workflow, not as a count derived by the observer.

Resolution events

pub struct ResolveAttemptEvent {
    pub template: String,
}

pub struct ResolveOutcomeEvent {
    pub resolved_path: Option<PathBuf>,
    pub attempted_paths: Vec<PathBuf>,
    pub code: Option<DiagnosticCode>,
}

ResolveOutcomeEvent represents both success and failure:

  • On success, resolved_path is expected to contain the selected path.
  • On failure, code can carry a stable diagnostic code.
  • attempted_paths preserves the candidates considered and is useful even when resolution succeeds.

Consumers should not infer failure solely from an empty attempted_paths; inspect resolved_path and code according to the reporting behavior they need.

Include-expansion event

pub struct IncludeOutcomeEvent {
    pub resolved_files: Vec<PathBuf>,
    pub include_chain: Vec<PathBuf>,
    pub code: Option<DiagnosticCode>,
}

A successful expansion can provide all resolved files. A failed expansion can provide the include chain and diagnostic code. Either vector may be empty, so consumers should not use vector length alone as the success signal.

Validation event

pub struct ValidationOutcomeEvent {
    pub warnings: Vec<Diagnostic>,
    pub errors: Vec<Diagnostic>,
}

Warnings and errors are deliberately separate. A consumer that only checks errors can preserve non-fatal diagnostic reporting; a consumer that treats any diagnostic as a failure should combine both lists explicitly.

This type derives PartialEq but not Eq, consistent with its Diagnostic payload.

Render event

pub struct RenderOutcomeEvent {
    pub rendered_bytes: Option<usize>,
    pub code: Option<DiagnosticCode>,
}

rendered_bytes reports output size when rendering succeeds; code records a stable diagnostic code when rendering fails. Consumers should handle the possibility that either optional field is absent rather than assuming they are strict inverses.

Dependencies

The production module depends only on:

  • std::path::PathBuf for filesystem-oriented resolution and include metadata.
  • serde::Serialize so event envelopes and payloads can be emitted as structured telemetry.
  • crate::Diagnostic and crate::DiagnosticCode for validation details and stable failure classification.

It does not import the CLI, logging framework, runtime integration, or composition engine. This preserves sc-composer as a reusable library and keeps host-specific policy at the boundary.

The module is consumed by the composer, resolver, validation, verification, frontmatter handling, and the sc-compose command layer. In particular, composition flows such as compose_with_observer and error-notification paths use CompositionObserver to report outcomes without coupling internal operations to a concrete reporter.

Test-only dependencies create temporary template roots and invoke compose directly. These tests verify that composition still works with no injected observer, that NoopObserver satisfies both traits, and that each callback/event variant can be accepted without side effects.

Usage Notes

Implement CompositionObserver when you only need selected lifecycle callbacks:

use sc_composer::{
    CompositionObserver, ResolveOutcomeEvent, ValidationOutcomeEvent,
};

struct DiagnosticsObserver;

impl CompositionObserver for DiagnosticsObserver {
    fn on_resolve_outcome(&mut self, event: &ResolveOutcomeEvent) {
        if let Some(code) = &event.code {
            eprintln!("resolution failed: {code:?}");
            for attempted in &event.attempted_paths {
                eprintln!("  attempted: {}", attempted.display());
            }
        }
    }

    fn on_validation_outcome(&mut self, event: &ValidationOutcomeEvent) {
        for warning in &event.warnings {
            eprintln!("warning: {warning:?}");
        }
    }
}

Implement ObservationSink when forwarding all telemetry through one pipeline:

use sc_composer::{ObservationEvent, ObservationSink};

struct JsonSink;

impl ObservationSink for JsonSink {
    fn emit(&mut self, event: &ObservationEvent) {
        match serde_json::to_string(event) {
            Ok(line) => println!("{line}"),
            Err(error) => eprintln!("failed to serialize observation: {error}"),
        }
    }
}

For a host that needs both semantic callbacks and a generic event collector, implement both traits on the same type. Do not assume implementing one trait automatically adapts to the other; NoopObserver implements both, but the traits are intentionally independent.

When storing events, clone them inside the callback or sink because all APIs provide borrowed references:

use sc_composer::{ObservationEvent, ObservationSink};

#[derive(Default)]
struct CapturingSink {
    events: Vec<ObservationEvent>,
}

impl ObservationSink for CapturingSink {
    fn emit(&mut self, event: &ObservationEvent) {
        self.events.push(event.clone());
    }
}

Avoid using telemetry as the authoritative source of composition state. Events describe lifecycle outcomes and diagnostic context, but the composition result and returned errors remain the primary control-flow interface. In particular:

  • Treat DiagnosticCode as stable classification data, not user-facing prose.
  • Preserve attempted_paths and include_chain order when presenting failures, since order conveys traversal context.
  • Keep observer implementations lightweight or buffer work for later; callbacks may be emitted from performance-sensitive composition paths.
  • Use NoopObserver or omit observer injection when instrumentation is unnecessary; the module’s tests establish that composition remains fully functional in that configuration.
