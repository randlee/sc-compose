Overview

render_many is the Application-layer edge connector for batch report rendering: it consumes a source-set definition and repository root, discovers matching text assets, renders each with a resolved template, and produces generated files plus a JSON manifest. It is imported across layer boundaries by the report-render command and reporting modules, making its request/result types part of the application-facing contract.

This is a hotspot for both change frequency and complexity. Changes can affect source discovery, path safety, template selection, rendering context, output layout, manifest compatibility, and CLI-visible errors at once.

The module supports two template modes:

  • A shared-report template receives the canonical report context built by context_from_source_entry, including a title derived by entry_title.
  • A regular loaded template receives an explicit JSON-compatible context containing source_path, output_path, metadata, sets, raw_source, and parsed body.

render_many first resolves a template, ensures the output root exists, discovers all globbed sources, sorts them deterministically by recorded source path, renders and writes each output, then writes <output_dir>/manifest.json. The result returns that manifest path, its entries, and every generated path including the manifest.

Public API

All symbols are pub(crate): accessible throughout sc-compose, but not exposed as a public Rust-library API.

Symbol Role
SourceSetDefinition Batch-render configuration: source-set id, source glob, template_selector, optional template_family, and relative output_dir.
RenderManyRequest Input to the batch renderer; combines the repository root with one source-set definition.
RenderManyRequest::output_extension Resolves the selected template and returns its output extension.
RenderManyManifestEntry Serializable manifest record containing relative source/output paths, source metadata, and optional set membership.
RenderManyResult Successful batch result containing the manifest path, manifest entries, and all generated outputs.
RenderManyError Error boundary for invalid globs, glob traversal, invalid/canonicalization paths, directory creation, output and manifest writes, JSON serialization, rendering, source loading, and template resolution.
render_many Main orchestration function for discovery, rendering, output persistence, and manifest creation.

Important internal helpers:

  • discover_sources canonicalizes the root, expands the configured glob, loads each SourceEntry, and derives its output path.
  • derive_output_path preserves the matched source’s relative directory structure below output_dir, replacing only its extension.
  • canonical_source_path and relative_source_path ensure matched inputs resolve beneath the canonical root.
  • render_entry selects the shared-context or generic-context rendering path.

The principal caller is commands/reports/render.rs, whose run_report_render_many command delegates batch work to render_many. The module also serves reporting catalog, index, initialization, and manifest-publication flows through its types and results.

Usage Notes

A caller constructs a request with paths relative to the report root:

let request = RenderManyRequest {
    root: project_root,
    source_set: SourceSetDefinition {
        id: "diagrams".to_owned(),
        glob: "reports/diagrams/**/*.mmd".to_owned(),
        template_selector: "templates/diagram.md.j2".to_owned(),
        template_family: None,
        output_dir: PathBuf::from("generated/diagrams"),
    },
};

let result = render_many(&request)?;

For a source such as reports/diagrams/system.mmd, a template whose extension resolves to md produces generated/diagrams/reports/diagrams/system.md. The relative source hierarchy is intentionally retained; callers should account for this when choosing output_dir.

Template-family resolution takes precedence over template_selector. If template_family is set, the selector is ignored by RenderManyRequest::resolve_template.

The output manifest is pretty-printed JSON at <output_dir>/manifest.json. Each entry preserves the source record’s paths, metadata, and optional sets; generated_outputs additionally includes the manifest itself. Consumers should use manifest_path for the canonical manifest location and not assume entries.len() equals generated_outputs.len().

Source discovery canonicalizes both the root and every glob result, then strips the canonical root prefix. This rejects paths that cannot be canonicalized or that resolve outside the configured root, including potential symlink escapes. The current error variant name, InvalidTemplatePath, covers these path-validation failures even though they may originate from source discovery.

Rendering order is deterministic because discovered entries are sorted by source path after glob expansion. This stabilizes manifest ordering and makes generated-output behavior more predictable across platforms and filesystems.

Generic templates receive:

source_path, output_path, metadata, sets, raw_source, body

sets is JSON null when no sets are present. Templates must therefore handle both null and an array. Shared-report templates receive the richer context produced elsewhere, so their available variables should be understood from report_context, not inferred from the generic list.

Filesystem writes are not transactional: outputs are written one at a time, and the manifest is written last. A failure can leave a partially generated output tree without a manifest, or with earlier outputs from the same run. Callers that require all-or-nothing publication should render into a staging directory and promote it separately.

Because this module is a high-activity hotspot, preserve these invariants when modifying it:

  • Keep path normalization and canonical-root containment checks intact.
  • Keep deterministic source ordering before manifest construction.
  • Preserve the manifest’s path serialization behavior.
  • Update both template modes when adding context fields or changing rendering semantics.
  • Treat template_family precedence and the manifest’s inclusion in generated_outputs as compatibility behavior.
