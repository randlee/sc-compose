Overview

diagnostics.rs is the Application-layer edge connector for structured library diagnostics, producing stable ERR_*/WARN_*/INFO_* records and versioned machine-readable payload envelopes for cross-layer callers. It provides the public contract shared by rendering, validation, include resolution, configuration handling, CLI reporting, and external bindings.

The module separates three concerns:

  • DiagnosticSeverity classifies a record as Error, Warning, or Info; its Display implementation emits lowercase text suitable for human-facing output.
  • DiagnosticCode supplies a finite, canonical taxonomy of machine-readable codes. as_str() maps each Rust variant to its stable all-caps identifier.
  • Diagnostic captures the code, severity, message, optional source location, and include provenance. DiagnosticEnvelope<T> packages arbitrary result data with diagnostics under a schema version.

The source-location fields are intentionally optional: failures such as invalid caller input or output writes may not map to a template file, while parser and include failures often do. The include chain is always present as a vector, avoiding an additional optional nesting for consumers.

Public API

DIAGNOSTIC_SCHEMA_VERSION

pub const DIAGNOSTIC_SCHEMA_VERSION: &str = "1";

The schema version embedded into every DiagnosticEnvelope<T>. Consumers of JSON output should use this field to select compatible decoding behavior rather than inferring schema shape from individual diagnostics.

DiagnosticSeverity

pub enum DiagnosticSeverity {
    Error,
    Warning,
    Info,
}

A serializable, deserializable severity classification. Serde uses lowercase values: "error", "warning", and "info".

Display emits the same lowercase strings. Use Error for fatal conditions, Warning for recoverable or fallback behavior that needs attention, and Info for non-failing observations such as default-value use.

DiagnosticCode

pub enum DiagnosticCode { /* stable code variants */ }

The canonical diagnostic taxonomy. Serde serializes variants in screaming-snake-case, matching as_str(). The codes cover:

  • Resolution: ERR_RESOLVE_NOT_FOUND, ERR_RESOLVE_AMBIGUOUS
  • Include safety and traversal: ERR_INCLUDE_ESCAPE, ERR_INCLUDE_NOT_FOUND, ERR_INCLUDE_CYCLE, ERR_INCLUDE_DEPTH
  • Template and input validation: ERR_VAL_*, WARN_VAL_CONFLICTING_DEFAULT_SECTIONS, INFO_VAL_DEFAULT_USED
  • Rendering and writes: ERR_RENDER_STDIN_DOUBLE_READ, ERR_RENDER_WRITE
  • Configuration and packs: ERR_CONFIG_* and WARN_CONFIG_SINGLE_PASS_ALL_FALLBACK

DiagnosticCode::as_str(self) -> &'static str returns the stable identifier without allocating. Prefer this method when formatting a code for a CLI message, lookup table, or non-Serde integration.

Adding a code extends a public machine-facing contract. Do not rename, remove, or repurpose an existing variant without considering JSON consumers, CLI tests, error-code documentation, and bindings.

Diagnostic

pub struct Diagnostic {
    pub severity: DiagnosticSeverity,
    pub code: DiagnosticCode,
    pub message: String,
    pub path: Option<PathBuf>,
    pub line: Option<usize>,
    pub column: Option<usize>,
    pub include_chain: Vec<PathBuf>,
}

A complete emitted diagnostic. The required fields establish stable programmatic meaning (severity, code) plus human context (message). The builder-style methods preserve the record when attaching optional provenance:

let diagnostic = Diagnostic::new(
    DiagnosticSeverity::Error,
    DiagnosticCode::ErrIncludeNotFound,
    "could not resolve partial 'header.jinja'",
)
.with_path("templates/page.jinja")
.with_location(12, 5)
.with_include_chain(vec![
    "templates/page.jinja".into(),
    "templates/layout.jinja".into(),
]);

with_location expects one-based line and column values. Callers must not pass zero-based offsets from parsers or byte positions without converting them. with_include_chain replaces the current chain rather than appending, so build the complete provenance sequence before calling it.

DiagnosticEnvelope<T>

pub struct DiagnosticEnvelope<T> {
    pub schema_version: String,
    pub payload: T,
    pub diagnostics: Vec<Diagnostic>,
}

A generic JSON-ready result wrapper. DiagnosticEnvelope::new(payload, diagnostics) sets schema_version from DIAGNOSTIC_SCHEMA_VERSION; callers supply their domain payload and all diagnostics emitted during the operation.

This supports successful operations with warnings or informational records as well as failed operations that have structured partial results. Consumers should inspect diagnostics by severity and code rather than treating a non-empty diagnostic list as automatically fatal.

Dependencies

The module has minimal direct dependencies:

  • serde::{Deserialize, Serialize} derives JSON-compatible serialization for severities, codes, records, and envelopes.
  • std::fmt implements Display for DiagnosticSeverity.
  • std::path::PathBuf represents owned source paths and include chains portably.

It is deliberately dependency-light because it forms a cross-layer public interface. It does not import rendering, parsing, filesystem, CLI, or error-framework types, preventing those concerns from leaking into the diagnostics contract.

Key consumers include:

  • Library internals: composer.rs, validation.rs, include.rs, resolver.rs, frontmatter.rs, error.rs, and verify.rs construct or inspect diagnostics while processing templates and inputs.
  • CLI code: main.rs, compose commands, reporting modules, and command-error handling surface codes and records to users and JSON outputs.
  • Tests: CLI and JSON CLI tests validate externally visible diagnostic behavior.
  • Bindings: Python enum support derives a stable string form from DiagnosticSeverity.

Usage Notes

Create diagnostics at the point where the system has the most accurate classification and provenance. For example, validation code should emit a specific ERR_VAL_* code rather than collapsing distinct failures into a generic message:

let diagnostic = Diagnostic::new(
    DiagnosticSeverity::Error,
    DiagnosticCode::ErrValMissingRequired,
    "required variable 'title' is missing",
)
.with_path(template_path);

For a render operation that can succeed with warnings:

let result = render_template(input)?;
let diagnostics = vec![Diagnostic::new(
    DiagnosticSeverity::Info,
    DiagnosticCode::InfoValDefaultUsed,
    "using default value for 'author'",
)];

let response = DiagnosticEnvelope::new(result, diagnostics);

When presenting an error to a human, use message for explanation and include code.as_str() so the output remains searchable and supportable. When writing automation, branch on DiagnosticCode or its stable string representation, not on message text; messages may evolve for clarity while codes are the compatibility boundary.

For include-related failures, attach both the immediate source path and the full include chain when available. This distinguishes the file that triggered resolution from the route through which it was reached, which is essential for diagnosing cycles, depth limits, and confinement escapes.

DiagnosticEnvelope<T> stores the schema version as an owned String, even though its source constant is static. This makes the envelope straightforward to serialize and deserialize as ordinary payload data. Construct envelopes with new instead of manually setting the version so all outputs stay aligned with the current schema constant.
