Project Summary

sc-compose consumes Jinja2-compatible template and profile files, YAML frontmatter, shared include fragments, and caller-supplied variables; it resolves and validates them through a deterministic composition pipeline and produces rendered text, structured diagnostics, verification results, report artifacts, and Python-callable results.

This Rust workspace provides a standalone template-composition toolchain for reusable prompts, configuration files, fixtures, reports, and other text assets. It supports explicit template paths and runtime-aware profile lookup, recursive @<path> includes, required-variable validation, multi-pass rendering, drift verification, and JSON-capable CLI output.

The repository ships the same composition semantics through three delivery surfaces:

  • sc-composer: the reusable Rust library and semantic source of truth.
  • sc-compose: the command-line application for local, scripted, and CI workflows.
  • bindings/python: PyO3/maturin bindings exposing the library to Python 3.11+.

The core is intentionally independent of orchestration runtimes: integrations construct composition requests outside this repository rather than adding runtime-specific dependencies to the renderer.

Core library: sc-composer

sc-composer owns the composition semantics and is designed for direct embedding. Its main pipeline is implemented by compose:

  1. Resolve either an explicit file or a runtime-aware profile path.
  2. Expand recursive @<path> includes within the configured workspace root.
  3. Parse YAML frontmatter and build the variable context.
  4. Validate declared, discovered, required, missing, and unknown variables.
  5. Render one or more template passes.
  6. Assemble optional guidance and user-prompt blocks.
  7. Return rendered output, resolved-file metadata, variable sources, warnings, or structured errors.

Key modules separate these responsibilities:

  • resolver: profile lookup policies and search traces.
  • include: include expansion, workspace confinement, cycle detection, and depth limits.
  • frontmatter: typed frontmatter parsing and normalization.
  • validation and validate: variable discovery, precedence rules, and validation reports.
  • renderer: MiniJinja-backed one-shot and long-lived rendering APIs.
  • composer: end-to-end orchestration and multi-pass execution.
  • verify: rendered-output comparison for drift detection.
  • diagnostics and error: stable machine-readable diagnostic and error contracts.
  • observer: library-local lifecycle events for host-provided telemetry without coupling the core to a logging implementation.

CLI layer: sc-compose

sc-compose is a thin UX and operational wrapper over sc-composer. It owns argument parsing, command routing, output formatting, exit-code behavior, output-file interactions, template-pack storage, bundled examples, and report workflows.

Command dispatch delegates composition work to the library while attaching a CLI-owned observer for structured logging. JSON output is wrapped in a consistent envelope so scripts and CI systems can consume diagnostics alongside command payloads.

The reporting subsystem is a separate CLI-facing workflow: it scaffolds report catalogs, renders specifications, materializes metadata, indexes current artifacts, verifies required evidence, and writes publish manifests for downstream handoff.

Python adapter: bindings/python

The Python package is an adapter, not a second implementation. Its Rust extension converts Python values into sc-composer request and result types, registers Python exceptions and enums, and exposes core functions such as rendering, composition, validation, resolution, include expansion, workspace initialization, and verification.

The package-level sc_compose module re-exports this native API, allowing Python applications to use the same validation and rendering behavior as the CLI.

Dependency boundaries

The intended dependency direction is:

sc-compose ───────► sc-composer
bindings/python ──► sc-composer

sc-composer must remain independent of the CLI, Python bindings, observability implementation details, and any external orchestration runtime. This preserves deterministic, reusable composition behavior across command-line, Python, and future embedded hosts.
