File: crates/sc-compose/src/reporting/spec.rs

Overview

reporting/spec.rs is the Application-layer edge connector for semantic report specifications: it parses TOML into typed state-machine or SQL-query models, renders Mermaid output, and materializes report artifacts and metadata for command-layer callers.

The module is the central boundary between user-authored semantic-spec TOML and the reporting pipeline. commands/reports/render.rs uses its execution entry point, while reporting peers consume its parsed ReportSpec model to validate, inspect, and render specs. It deliberately keeps the supported spec kinds explicit and finite:

  • state_machine maps directly to StateMachineSpec.
  • sql_query maps through the private RawSqlQuerySpec wire format, then is normalized into SqlQuerySpec.

A spec must define a [spec] table with a supported kind. Documents without that table or without spec.kind are treated as non-spec inputs (Ok(None)), while malformed TOML and unknown kinds are reported as errors.

Public API

All items are pub(crate): available throughout the sc-compose crate but not exported as a public library API.

Data models

Symbol Purpose
SpecHeader Common identity and presentation fields: kind, id, title, and optional renderer_targets.
ReportSpecMetadata Optional shared metadata: owners, tags, renderer_targets, and sets.
StateMachineState A state identifier, optional display label, and terminal-state flag.
StateMachineTransition Directed state transition with optional event, guard, actor, and effect annotations.
StateMachineSpec State-machine report body: header, states, transitions, and metadata.
SqlQuerySpec Normalized SQL-query report body: purpose, table access, filtering, ordering, cardinality, transactional assumptions, and metadata.
ReportSpec Tagged union over supported report kinds: StateMachine and SqlQuery.
ReportSpecError Parsing, unsupported-kind, and JSON-serialization failures.

RawSqlQuerySpec and SqlQueryFields are private deserialization helpers. They accept SQL-query details nested beneath [sql_query], then flatten those values into the public-internal SqlQuerySpec structure.

parse_report_spec

pub(crate) fn parse_report_spec(
    raw_source: &str,
) -> Result<Option<ReportSpec>, ReportSpecError>

Parses semantic-spec TOML.

Behavior:

  1. Parses raw_source as toml::Value.
  2. Looks for [spec] and spec.kind.
  3. Returns Ok(None) when either is absent.
  4. Deserializes supported kinds into a ReportSpec.
  5. Returns UnsupportedKind for an unrecognized kind.

Callers such as reporting::source_entry use the Option result to distinguish ordinary TOML sources from semantic report specs. The command execution path treats None as invalid because rendering specifically requires a semantic spec.

run_render_spec_report

pub(crate) fn run_render_spec_report(
    root: &Path,
    spec_path: &Path,
    archive: bool,
) -> Result<ReportsSmokeResult, CommandError>

Executes the complete single-spec rendering workflow:

  1. Canonicalizes root.
  2. Resolves spec_path safely relative to that workspace.
  3. Reads and parses the TOML spec.
  4. Renders Mermaid via reporting::mermaid::render_mermaid.
  5. Writes reports/latest/<report-id>/index.mmd.
  6. Writes metadata and, when requested, archives artifacts through write_report_metadata_and_archive.
  7. Returns the resulting ReportsSmokeResult.

Filesystem, parsing, rendering, and output-materialization failures are converted to CommandError values with diagnostic codes appropriate for command handling.

ReportSpec helpers

Method Result
report_id() Returns the common spec.id.
title() Returns the common spec.title.
kind_name() Returns "state_machine" or "sql_query".
renderer_targets() Returns effective renderer targets. Metadata targets override header targets when non-empty.
report_metadata() Produces a deterministic BTreeMap<String, serde_json::Value> containing title, kind, ID, effective targets, and a JSON copy of the complete spec.
sets() Returns None for no configured sets, otherwise a cloned list of metadata sets.

report_metadata() can fail only when serializing renderer targets or the full ReportSpec to JSON.

Dependencies

Internal reporting collaborators

  • reporting::mermaid::render_mermaid converts the parsed ReportSpec into Mermaid text. Its validation errors are surfaced by run_render_spec_report as command errors.
  • reporting::path::resolve_relative_path resolves the requested spec path under the canonical workspace root.
  • reporting::output::write_report_metadata_and_archive records report metadata and handles optional archival.
  • reporting::init::ReportsSmokeResult is the execution result returned to the caller.
  • CommandError standardizes CLI/application error classification.

External crates and standard library

  • toml parses the input document and deserializes typed spec structures.
  • serde derives TOML/JSON serialization and deserialization behavior.
  • serde_json builds report metadata and embeds the complete spec as JSON.
  • sc_composer::DiagnosticCode supplies diagnostic codes for configuration-related errors.
  • anyhow adds contextual error messages.
  • BTreeMap provides stable key ordering for metadata.
  • Path and PathBuf represent workspace-relative and materialized artifact paths.

Usage Notes

State-machine spec example

[spec]
kind = "state_machine"
id = "checkout-flow"
title = "Checkout lifecycle"
renderer_targets = ["mermaid"]

[[states]]
id = "pending"
label = "Pending"

[[states]]
id = "paid"
terminal = true

[[transitions]]
from = "pending"
to = "paid"
event = "payment_captured"

[metadata]
owners = ["payments"]
tags = ["checkout", "state-machine"]
sets = ["commerce"]

Parsing this source produces ReportSpec::StateMachine. Rendering writes Mermaid to:

reports/latest/checkout-flow/index.mmd

The output helper additionally creates report metadata, including the original normalized spec in the copy_json field.

SQL-query spec example

[spec]
kind = "sql_query"
id = "active-orders"
title = "Active orders query"

[sql_query]
purpose = "List currently active orders"
tables_read = ["orders"]
tables_written = []
filters = ["status = 'active'"]
ordering = ["created_at DESC"]
cardinality = "many"
transactional_assumptions = ["Read committed is sufficient"]

[metadata]
renderer_targets = ["mermaid"]
tags = ["orders", "sql"]

Although the input uses a nested [sql_query] table, the parser normalizes it into a flat SqlQuerySpec payload under ReportSpec::SqlQuery. This makes downstream consumers independent of the TOML nesting used for deserialization.

Renderer-target precedence

metadata.renderer_targets takes precedence over spec.renderer_targets, but only if the metadata list is non-empty. An empty metadata list does not clear header targets; it falls back to the header value.

This is important when generating metadata or selecting renderers: use ReportSpec::renderer_targets() rather than reading either source field directly.

Input and error handling pitfalls

  • parse_report_spec returning Ok(None) does not mean the document is valid for rendering. It only means it is not recognized as a semantic spec. run_render_spec_report rejects this case.
  • An unknown spec.kind is an error, not an ignored document. This protects users from silently misspelled kinds.
  • state_machine requires the layout expected by StateMachineSpec; Mermaid rendering performs additional semantic validation, such as requiring states.
  • SQL query fields such as purpose and cardinality are required by the deserialization model, while list fields use serde defaults and may be omitted.
  • Report IDs become path segments beneath reports/latest; callers should ensure IDs are suitable for the project’s expected report naming conventions.
  • Output failures are reported separately as render-write or configuration-related command errors, retaining path-specific context for CLI diagnostics.
