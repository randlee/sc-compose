File: crates/sc-composer/src/types.rs

Overview

types.rs is the Application-layer edge-connector contract module: it consumes caller configuration and render inputs and produces the validated request, policy, trace, diagnostic, and result types shared across sc-composer and cross-layer consumers. It is a high-activity, high-complexity hotspot, so changes can affect composition, validation, resolution, frontmatter processing, verification, workspace initialization, and CLI commands.

The module establishes the library’s stable public data model:

  • Input validation: InputValue, YAML conversion, and shape-validation errors.
  • Safe identifiers and paths: VariableName, ProfileName, IncludeDepth, and ConfiningRoot.
  • Composition configuration: runtime/profile selection, ComposeMode, resolver and variable policies, and multi-pass settings.
  • Request and outcome contracts: ComposeRequest, ComposeResult, ValidationReport, ResolveResult, VerifyResult, and initialization results.
  • Provenance and diagnostics: VariableSource plus typed validation errors and Diagnostic collections.

default_pass_number() centralizes pass numbering at 1. Both PassConfig::default and deserialization use it; a serialized pass_number: 0 is normalized to that default. This prevents frontmatter and request policy from interpreting omitted or zero-valued passes differently.

Input values are intentionally narrower than arbitrary JSON/YAML. Scalars and objects are supported, as are top-level arrays of objects, but nested arrays and arrays of objects below the top level are rejected. YAML mappings must have string keys, and YAML is converted to serde_json::Value before use as render input.

Public API

Input and metadata

  • type InputValue = serde_json::Value is the caller-provided render-context value.
  • validate_input_value(&InputValue) validates supported JSON shapes before rendering.
  • input_value_from_yaml(serde_yaml::Value) converts supported YAML into InputValue, rejecting non-string keys and unsupported nesting.
  • MetadataValue wraps YAML values used only for descriptive frontmatter metadata; to_json_value() exposes a JSON-compatible representation when possible.
  • InvalidInputValueError carries a stable DiagnosticCode and human-readable message.

Validated value objects

  • VariableName::new(...) accepts only non-empty ASCII alphanumeric names plus _, -, and .. It implements Display and TryFrom<String> / TryFrom<&str>.
  • ProfileName::new(...) accepts non-empty names without / or \, preventing path traversal through profile-mode resolution.
  • IncludeDepth wraps a non-negative u16 depth limit.
  • ConfiningRoot::new(...) canonicalizes a filesystem root for include and template-resolution confinement. from_path_buf(...) is for callers that already hold a canonical path.

Requests and policy

  • RuntimeKind selects a runtime layout: Claude, Codex, Gemini, or Opencode.
  • ProfileKind selects Agent, Command, or Skill prompt profiles.
  • ComposeMode selects either:
  • Profile { kind, name } for profile lookup, or
  • File { template_path } for direct template composition.
  • UnknownVariablePolicy controls extra caller variables: Error, Warn, or Ignore (default).
  • ResolverPolicy holds ordered candidate directories, filename probes, and ambiguity behavior.
  • PassConfig supplies per-pass required variables, defaults, and metadata.
  • ComposePolicy bundles undeclared-variable behavior, unknown-variable policy, include depth, allowed roots, resolver policy, and pass configuration.
  • ComposeRequest is the main input to compose and validation entry points. It carries the mode, root, optional runtime, variable maps from explicit/environment/default sources, optional appended guidance and user prompt blocks, and policy.

Results and tracing

  • VariableSource records which source won during variable resolution.
  • ResolveResult records the final path, all attempted paths, and ambiguity candidates.
  • ComposeResult returns rendered text, resolved files, resolution trace, variable provenance, and warnings.
  • ValidationReport returns validation status, warnings, errors, and resolution trace without rendered output.
  • VerifyResult reports template drift, compared paths and contents, optional unified diff, and warnings.
  • FrontmatterInitResult and InitResult define result contracts for initialization-oriented helpers.

Dependencies

The module depends on:

  • serde for serializing public request/result contracts and deserializing policy/frontmatter data.
  • serde_json as the render-context representation behind InputValue.
  • serde_yaml for frontmatter and metadata conversion.
  • crate::diagnostics::{Diagnostic, DiagnosticCode} for stable diagnostics embedded in errors and result collections.
  • Standard-library BTreeMap for deterministic variable/default/provenance maps and PathBuf/Path for filesystem-facing request and resolution data.

It is imported by the composer, resolver, frontmatter, include, validation, verification, workspace-initialization, and error modules. The CLI’s template_init command also imports it across the layer boundary, making API changes here externally consequential.

Usage Notes

Construct names and roots through their validating constructors rather than their internal representations:

use sc_composer::{ConfiningRoot, ProfileName, VariableName};

let root = ConfiningRoot::new("./prompts")?;
let profile = ProfileName::new("release-notes")?;
let variable = VariableName::new("pr.number")?;

Validate every externally supplied JSON input before placing it into a request. This is especially important for CLI variable files and manifest defaults, which call into this module’s validator.

use sc_composer::{validate_input_value, InputValue};

let value: InputValue = serde_json::json!({
    "pr": {
        "number": 43,
        "labels": ["bug", "release"]
    }
});

validate_input_value(&value)?;

Top-level arrays of objects are valid, enabling batch-style render inputs. Do not rely on nested arrays, including arrays inside object members; they fail with ErrValNestedArrayUnsupported. YAML callers should use input_value_from_yaml so that mapping-key and nesting rules are enforced during conversion.

Compose requests should keep variable sources separate. Put direct user input in vars_input, inherited environment values in vars_env, and CLI or pack defaults in vars_defaults; the returned variable_sources map then explains which source supplied each resolved value.

When deserializing PassConfig, treat 0 as equivalent to an omitted pass number. If code needs an explicit default, call default_pass_number() instead of duplicating 1; this is relied on by frontmatter normalization and the CLI initialization flow.

Configure allowed_roots with canonical ConfiningRoot values whenever file resolution crosses user-controlled paths. ProfileName rejects path separators, but file-mode composition still needs root confinement through ComposeRequest.root and policy roots.
