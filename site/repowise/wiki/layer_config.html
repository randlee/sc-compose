Layer: Config

I’ll inspect the configuration and agent-control files, then produce a grounded architectural overview.

Overview

The Config layer is the repository’s control-plane configuration layer: it defines build overrides, AI-agent profiles, workflow prompts, reusable skills, and QA/release policies consumed by Cargo, Claude-compatible runtimes, and sc-compose profile resolution. It contains declarative Markdown, YAML, TOML, and Jinja templates rather than application runtime logic.

Key Components

  • .cargo/config.toml patches the sc-composer crates.io dependency to the workspace-local crates/sc-composer, ensuring Cargo builds use the checked-out library.
  • .claude/CLAUDE.md supplies repository guidance and Repowise indexing metadata, including architecture, tooling, hotspot, and edit-workflow instructions.
  • .claude/agents/registry.yaml is the inventory of named agents and skills, with versions, paths, and dependency declarations.
  • Agent definitions provide narrowly scoped control roles:
  • quality-mgr.md coordinates multi-reviewer QA and enforces a hard merge gate.
  • arch-qa.md evaluates structural boundaries and architectural fitness independently of functional correctness.
  • flaky-test-qa.md audits nondeterminism, races, lifecycle cleanup, and environment isolation.
  • qa-triage.md correlates a finding across worktrees and records canonical Turtle facts under .triage/.
  • plan-scope-reviewer.md and critical-plan-reviewer.md harden sprint plans before implementation.
  • publisher.md governs release preflight, workflow-driven publishing, and distribution verification.
  • .claude/skills/ packages reusable workflows, assignment/report templates, reviewer guidance, and Rust quality references. codex-orchestration defines the development-to-QA loop; plan-hardening defines staged plan review; quality-management-gh defines multi-pass QA and PR reporting.
  • .claude/commands/ contains user-invocable operational prompts, while .claude/assets/ supplies templates consumed by the quality-management workflow.

Data Flow

Cargo build
  -> .cargo/config.toml
  -> workspace-local sc-composer

AI runtime / sc-compose profile lookup
  -> runtime search chain
  -> .claude/{agents,commands,skills} fallback
  -> agent prompt, command, or SKILL.md/template

Team-lead assignment
  -> orchestration XML/JSON templates
  -> developer or reviewer agent
  -> quality-mgr reviewer fan-out
  -> structured PASS / FAIL / IN-FLIGHT result
  -> PR and release gates

For profile resolution, .claude/ is the native source for Claude and the universal fallback for Codex, Gemini, and OpenCode after their runtime-specific and shared .agents/ locations. sc-composer owns that resolver policy; this layer supplies the discoverable profile content.

The planning workflow routes a source-of-truth sprint plan through plan-scope and critical review, then into QA. Implementation QA expands to the sprint diff, dispatches the required specialist reviewers, gathers structured findings, and blocks merge until requirements traceability and deliverable completion reach 100%. QA triage persists cross-worktree evidence as per-finding Turtle records for later aggregation.

Architecture Notes

  • This layer is declarative infrastructure, not part of the sc-composer rendering pipeline or the sc-compose CLI implementation. Its relationship to those crates is configuration and profile content, except for Cargo’s local dependency patch.
  • The registry is metadata, not a runtime dispatcher: agent behavior is defined in the referenced Markdown files, and workflow composition is defined by the skill templates.
  • Agent prompts use strict input and output contracts—primarily XML or fenced JSON—to preserve handoff structure between planning, development, QA, and release roles.
  • Quality responsibilities are deliberately separated: requirements conformance, structural compliance, test stability, and release execution are distinct checks. quality-mgr aggregates their results but is not authorized to implement fixes.
  • Several agent rules reference broader ATM-style workflows and paths; these are governance instructions in prompt content, not dependencies of the standalone sc-compose binaries.
