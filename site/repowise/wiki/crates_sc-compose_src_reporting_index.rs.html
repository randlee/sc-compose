Overview

reporting/index.rs is the Application-layer entry point and cross-layer edge connector for report-evidence indexing: it consumes the report catalog and report metadata beneath a repository root and produces serializable report-index and required-report verification results. It is called by the reports CLI commands and publish-manifest writer, giving those consumers one consistent view of each configured report’s declared paths, metadata-derived state, artifacts, and missing evidence.

The module joins two sources of truth:

  • The catalog supplies the report identity, kind, required flag, entrypoint path, and metadata path.
  • The metadata JSON supplies the runtime status, produced_at timestamp, and artifact paths—but is read only after the declared entrypoint and metadata file both exist.

Each ReportIndexEntry preserves catalog information even when evidence is incomplete. Instead of failing immediately for absent entrypoints, metadata files, or artifacts, indexing records relative paths in missing_paths. This permits index consumers to display the complete report inventory, including broken or incomplete entries. Strict enforcement is deferred to verify_required_reports, which fails only when a required report has missing evidence.

All paths stored in index output are relative PathBuf values and are serialized through the project’s path helpers, allowing JSON output to use platform-independent path formatting.

Public API

ReportIndexEntry

A serializable, per-report evidence record.

Field Source Meaning
report_id catalog Configured report identifier.
kind catalog Catalog-defined report type.
required catalog Whether missing evidence must cause verification failure.
status metadata Metadata status when the entrypoint and metadata file are present; otherwise None.
produced_at metadata Metadata production timestamp when metadata is readable and valid; otherwise None.
entrypoint catalog Relative path to the report’s primary evidence file.
metadata catalog Relative path to the report metadata JSON file.
artifacts metadata Relative paths declared by metadata; empty when prerequisite files are missing.
missing_paths indexer Missing declared or metadata-listed paths, relative to root.

status, produced_at, and artifacts are not independently best-effort fields. If either the configured entrypoint or configured metadata file is absent, the module skips metadata parsing entirely and leaves all three in their empty/None form.

ReportIndex

A serializable wrapper around the complete catalog-derived index:

pub(crate) struct ReportIndex {
    pub(crate) entries: Vec<ReportIndexEntry>,
}

Entries retain catalog iteration order. The module does not sort, deduplicate, or filter the catalog; catalog validation is delegated to ReportCatalog::load.

ReportVerifyResult

A serializable verification summary:

pub(crate) struct ReportVerifyResult {
    pub(crate) required_count: usize,
    pub(crate) verified_count: usize,
}

On success, verified_count equals required_count. If an invalid required entry is found, verification returns an error immediately instead of producing a partial result.

ReportIndexError

The module’s error type covers four failure classes:

  • Catalog(Box<CatalogError>) — the report catalog cannot be loaded or validated.
  • ReadMetadata { path, source } — a metadata file expected to exist cannot be read.
  • ParseMetadata { path, source } — metadata exists but is not valid ReportMetadata JSON.
  • MissingRequiredEvidence { report_id, missing_paths } — verification found absent evidence for a required report.

Display retains file paths and underlying I/O or JSON errors. MissingRequiredEvidence formats every missing path as a comma-separated list. The type implements std::error::Error, allowing command-layer callers to convert it into their diagnostic mechanism.

build_report_index

pub(crate) fn build_report_index(root: &Path) -> Result<ReportIndex, ReportIndexError>

Loads the report catalog rooted at root, indexes every report definition, and returns all entries.

Processing for each report is:

  1. Check whether root / entrypoint exists.
  2. Check whether root / metadata exists.
  3. If either is missing, record the missing declared path or paths and do not parse metadata.
  4. Otherwise, read and deserialize metadata.
  5. Copy its status, produced_at, and artifact paths into the index entry.
  6. Check every metadata artifact path under root and append absent artifacts to missing_paths.

The function surfaces malformed or unreadable metadata as errors rather than representing it as “missing.” This distinction matters operationally: an absent evidence path is an indexable state, while inaccessible or invalid metadata means the report’s declared evidence cannot be interpreted safely.

verify_required_reports

pub(crate) fn verify_required_reports(root: &Path) -> Result<ReportVerifyResult, ReportIndexError>

Builds the full index, filters it to required entries, and confirms that each has an empty missing_paths list.

The first required entry with missing evidence causes MissingRequiredEvidence; later required entries are not examined. Optional reports remain part of build_report_index output but cannot fail this verification operation.

Internal helpers

index_entry performs the per-definition filesystem and metadata checks. It is private so callers cannot bypass catalog loading or construct a partial index workflow.

read_metadata reads root.join(relative_path) as bytes and deserializes ReportMetadata with serde_json::from_slice. It preserves the resolved path in either read or parse errors.

Dependencies

Internal modules

  • reporting::catalog::{CatalogError, ReportCatalog} provides validated report definitions. Catalog validation establishes constraints such as supported report kinds, unique IDs, and normalized relative entrypoint and metadata paths before this module accesses the filesystem.
  • reporting::output::ReportMetadata defines the JSON schema emitted for materialized reports. This module consumes its status, produced_at, and artifacts fields.
  • path_utils::serialize_path and path_utils::serialize_paths are referenced by Serde attributes to normalize serialized path representation.

External and standard-library dependencies

  • serde::Serialize makes all public result records suitable for CLI JSON output and manifest generation.
  • serde_json parses report metadata.
  • std::path::{Path, PathBuf} represents the repository root and catalog-relative evidence paths.
  • std::fs::read reads metadata files.
  • std::fmt and std::error::Error provide diagnostic integration.

Consumers

  • commands/reports/scaffold.rs calls build_report_index for the reports index command and verify_required_reports for the reports verification command.
  • reporting/publish_manifest.rs calls build_report_index before writing the publish manifest.
  • reporting/mod.rs exposes the module within the reporting subsystem.
  • main.rs reaches this functionality indirectly through command dispatch.

Usage Notes

Index reports for presentation or downstream generation

Use build_report_index when a caller needs visibility into both complete and incomplete reports.

let index = build_report_index(repo_root)?;

for entry in &index.entries {
    println!("{}: {} missing paths", entry.report_id, entry.missing_paths.len());

    if let Some(status) = &entry.status {
        println!("  status: {status}");
    }
}

This is appropriate for a JSON index command or publish-manifest preparation because consumers can inspect all catalog entries and decide how to represent optional missing evidence.

Verify required evidence before a gated workflow

Use verify_required_reports when only required reports should block progress.

match verify_required_reports(repo_root) {
    Ok(result) => {
        println!(
            "verified {}/{} required reports",
            result.verified_count,
            result.required_count
        );
    }
    Err(ReportIndexError::MissingRequiredEvidence {
        report_id,
        missing_paths,
    }) => {
        eprintln!("required report {report_id} is incomplete: {missing_paths:?}");
    }
    Err(error) => return Err(error.into()),
}

A successful verification result does not imply optional reports are complete. To audit those too, build and inspect the full index.

Interpret missing_paths correctly

missing_paths can contain:

  • the catalog-defined entrypoint;
  • the catalog-defined metadata path;
  • artifact paths listed inside valid metadata.

If the entrypoint or metadata path is missing, artifacts are intentionally not discovered, because metadata parsing is skipped. Consequently, the list reports directly observable missing evidence only; it is not a speculative list of artifacts that might have been present in unavailable metadata.

Treat parsing failures differently from absent files

A missing metadata file is recorded in missing_paths and can be tolerated for optional reports. A metadata file that exists but cannot be read or parsed returns an error from build_report_index, including for optional reports. Callers that need a resilient user-facing command should render ReportIndexError as a configuration/evidence diagnostic rather than silently omitting the report.

Preserve root-relative semantics

The catalog is responsible for enforcing normalized relative paths. This module joins each configured or metadata-derived path to root; callers should pass the intended repository root, not an individual report directory. Passing the wrong root can make otherwise valid relative paths appear missing.

Be aware of early-exit verification

verify_required_reports stops at the first required entry with missing evidence. It is efficient for command gating but does not aggregate all required-report failures. A caller that needs a complete remediation report should call build_report_index, filter entry.required && !entry.missing_paths.is_empty(), and collect every failure itself.
