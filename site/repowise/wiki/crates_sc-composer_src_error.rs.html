File: crates/sc-composer/src/error.rs

Overview

error.rs is the Application-layer error adapter that converts resolution, include, validation, rendering, and configuration failures into stable crate-owned error values consumed by sc-composer entry points and callers. It centralizes diagnostic codes, contextual failure data, chained sources, captured backtraces, and structured recovery guidance so the composition pipeline exposes one coherent failure contract.

The module defines five domain-specific families:

  • ResolveError records failed profile/file resolution, including every attempted path.
  • IncludeError records include-expansion failures and the include chain that produced them.
  • ValidationError preserves a full set of Diagnostic values and optional recovery hints.
  • RenderError wraps template-engine failures without exposing engine-specific error types.
  • ConfigError represents configuration and parsing failures, optionally with recovery hints.

ComposeError is the public top-level sum type returned by compose, validate, and related helper entry points. It carries one of the five families and provides a uniform code() accessor and standard Rust error chaining through std::error::Error.

All error families capture a Backtrace when constructed. Resolution, include, validation, and configuration errors use the shared display formatter, which prints the message, recursively enumerates source causes, and appends the backtrace. Rendering intentionally uses a shorter display form—template rendering failed: …—while retaining the original source as its Error::source().

Validation failures can be constructed from individual conditions or from an entire diagnostics collection. ValidationError::from_diagnostics chooses the first diagnostic’s code (or ErrValEmpty for an empty collection), formats all diagnostics into the message, preserves the original collection, and adds an InspectPath recovery hint when any diagnostic has a path.

Public API

RecoveryHint and RecoveryHintKind

RecoveryHint is a public, cloneable structured recommendation attached to configuration and validation failures.

pub struct RecoveryHint {
    pub kind: RecoveryHintKind,
}

RecoveryHint::new(kind) constructs a hint. The payload enum distinguishes actionable next steps:

Variant Payload Meaning
RunCommand command: String Suggest a command to run.
InspectPath path: PathBuf Direct the caller to inspect a relevant file or path.
ProvideVariable variable: VariableName Identify a missing input variable.
ReviewConfiguration key: String Point to a configuration key needing correction.

Consumers should pattern-match on hint.kind instead of parsing error text. This keeps remediation workflows stable even if human-readable messages change.

ResolveError

Represents resolution failures, such as a missing template or profile.

Public inspection methods:

error.code() -> DiagnosticCode
error.attempted_paths() -> &[PathBuf]
error.message() -> &str
error.backtrace() -> &Backtrace

Its constructors are pub(crate), so other crate modules create it with a diagnostic code, message, and attempted paths; external callers receive it through ComposeError or a public API result. with_source attaches an underlying I/O or related error while retaining the resolution-specific context.

IncludeError

Represents include expansion failures, including root-escape or nested include problems.

error.code() -> DiagnosticCode
error.include_chain() -> &[PathBuf]
error.message() -> &str
error.backtrace() -> &Backtrace

The include chain is distinct from a generic source chain: it explains the template inclusion path that led to the failure. Use it to render a template-level trace for users.

ValidationError

Represents invalid frontmatter, variable declarations, input-value shapes, and aggregated validation diagnostics.

error.code() -> DiagnosticCode
error.recovery_hints() -> &[RecoveryHint]
error.diagnostics() -> &[Diagnostic]
error.message() -> &str
error.backtrace() -> &Backtrace

Internally available constructors include:

ValidationError::new(code, message)
ValidationError::from_diagnostics(diagnostics)
ValidationError::duplicate_variable(&variable)
ValidationError::invalid_input_value(code, message)

from_diagnostics is the preferred path when validation discovers multiple issues. It preserves every diagnostic rather than collapsing them into one text-only error.

duplicate_variable specifically emits ErrValDuplicate and adds:

RecoveryHintKind::ReviewConfiguration {
    key: "required_variables".to_owned(),
}

RenderError

Represents template compilation or rendering failures.

error.backtrace() -> &Backtrace
error.code() -> Option<DiagnosticCode>
error.message() -> &str

RenderError is deliberately opaque to external callers. Its crate-private render(source) constructor accepts any thread-safe standard error, snapshots its string message, and boxes the original error as the source. Its diagnostic code is currently absent by default (None), so callers must handle render failures that have no stable DiagnosticCode.

ConfigError

Represents configuration and parsing failures.

error.code() -> DiagnosticCode
error.recovery_hints() -> &[RecoveryHint]
error.message() -> &str
error.backtrace() -> &Backtrace

Crate modules construct it with new, may add a source through with_source, and may attach one or more structured recovery hints with with_recovery_hint.

ComposeError

The top-level error enum unifies the library’s public failure paths:

pub enum ComposeError {
    Resolve(ResolveError),
    Include(IncludeError),
    Validation(Box<ValidationError>),
    Render(RenderError),
    Config(ConfigError),
}

All five concrete error types implement From<T> for ComposeError, allowing crate code to use ? when a function returns Result<_, ComposeError>.

fn run() -> Result<(), ComposeError> {
    let result = perform_composition()?;
    consume(result);
    Ok(())
}

ComposeError::code() returns:

  • Some(code) for resolve, include, validation, and configuration errors.
  • The render error’s optional code, currently normally None.

The Validation variant boxes ValidationError, reducing the enum’s inline size and avoiding a large top-level error value because validation errors retain vectors of diagnostics and recovery hints.

Dependencies

The module depends only on standard-library error infrastructure and internal Application-layer types:

  • std::error::Error, std::fmt, and Box<dyn Error + Send + Sync> provide standard error interoperability, formatting, and source storage.
  • std::backtrace::Backtrace captures failure-origin context at construction time.
  • std::path::PathBuf stores attempted resolver paths, include chains, diagnostic paths, and path-oriented hints.
  • crate::diagnostics::DiagnosticCode supplies stable machine-readable error identities.
  • crate::Diagnostic supplies full validation diagnostics, including message, path, line, column, and include-chain context.
  • crate::types::VariableName provides validated variable identifiers for recovery hints and duplicate-variable validation errors.

Upstream modules use the families according to their responsibility:

  • resolver.rs constructs ResolveError values with candidate paths.
  • include.rs constructs IncludeError values with include chains.
  • frontmatter.rs, validation.rs, and verify.rs produce validation and configuration failures.
  • renderer.rs converts engine failures into RenderError.
  • composer.rs and lib.rs expose unified ComposeError results.
  • sc-compose’s CLI entry point can inspect the top-level error and render user-facing diagnostics without depending on template-engine error types.

Usage Notes

Handle failures by variant, then prefer structured fields

Use ComposeError for broad control flow, then inspect the variant-specific data when presenting diagnostics or deciding remediation.

match error {
    ComposeError::Resolve(error) => {
        eprintln!("{} ({})", error.message(), error.code().as_str());

        for path in error.attempted_paths() {
            eprintln!("  tried {}", path.display());
        }
    }
    ComposeError::Include(error) => {
        eprintln!("{} ({})", error.message(), error.code().as_str());

        for path in error.include_chain() {
            eprintln!("  included from {}", path.display());
        }
    }
    ComposeError::Validation(error) => {
        for diagnostic in error.diagnostics() {
            eprintln!("{}: {}", diagnostic.code.as_str(), diagnostic.message);
        }

        for hint in error.recovery_hints() {
            match &hint.kind {
                RecoveryHintKind::InspectPath { path } => {
                    eprintln!("Inspect {}", path.display());
                }
                RecoveryHintKind::ProvideVariable { variable } => {
                    eprintln!("Provide {variable}");
                }
                RecoveryHintKind::ReviewConfiguration { key } => {
                    eprintln!("Review configuration key {key}");
                }
                RecoveryHintKind::RunCommand { command } => {
                    eprintln!("Run: {command}");
                }
            }
        }
    }
    ComposeError::Render(error) => {
        eprintln!("{}", error.message());
    }
    ComposeError::Config(error) => {
        eprintln!("{} ({})", error.message(), error.code().as_str());
    }
}

Do not infer attempted paths, include ancestry, or recovery steps from Display output. Those details have dedicated accessors intended for programmatic consumers.

Preserve all validation diagnostics

For validation workflows, ValidationError::diagnostics() is more authoritative than message(). The message is a formatted summary, while the diagnostics slice retains structured fields such as code, location, path, and include chain.

An empty diagnostics set is valid at construction time. In that case, from_diagnostics assigns DiagnosticCode::ErrValEmpty and produces an empty message. Consumers that render validation output should therefore handle an empty diagnostics slice rather than assuming at least one entry.

Understand diagnostic-code availability

Most concrete families guarantee a DiagnosticCode. RenderError does not: RenderError::code() returns Option<DiagnosticCode> and currently defaults to None.

if let Some(code) = error.code() {
    telemetry.record_code(code.as_str());
} else {
    telemetry.record_unclassified_failure();
}

Avoid treating a missing code as a success condition or as an unreachable state; it is the expected representation of an engine-originated render failure that has not been classified.

Use standard error chaining for root-cause reporting

All families implement std::error::Error, and their optional boxed source errors are exposed through source(). Generic Rust error-reporting tools can traverse the chain without knowing this module’s concrete types.

ResolveError, IncludeError, ValidationError, and ConfigError include the chain and captured backtrace in their Display output. This is useful for terminal diagnostics but can be verbose; structured accessors are preferable for compact or machine-readable output.

RenderError is an important exception: its display text does not include its captured backtrace. Obtain it explicitly through backtrace() if a renderer or telemetry sink needs it.

Build a validation remediation flow

A robust caller can combine diagnostics and recovery hints in stages:

  1. Read ValidationError::diagnostics() to report every invalid condition.
  2. Use each Diagnostic’s location and include-chain data to identify the source template.
  3. Match RecoveryHintKind to generate focused next actions.
  4. Fall back to message() only for a concise plain-text summary.
fn remediation(error: &ValidationError) -> Vec<String> {
    let mut actions = Vec::new();

    for hint in error.recovery_hints() {
        match &hint.kind {
            RecoveryHintKind::InspectPath { path } => {
                actions.push(format!("Open {}", path.display()));
            }
            RecoveryHintKind::ProvideVariable { variable } => {
                actions.push(format!("Supply required variable `{variable}`"));
            }
            RecoveryHintKind::ReviewConfiguration { key } => {
                actions.push(format!("Review `{key}`"));
            }
            RecoveryHintKind::RunCommand { command } => {
                actions.push(format!("Run `{command}`"));
            }
        }
    }

    actions
}

Avoid constructing public errors outside the crate

The concrete error constructors are intentionally pub(crate). External integrations should not attempt to recreate resolver, include, validation, render, or configuration errors from strings. Instead, consume ComposeError from the library’s public operations, preserving the crate’s diagnostic-code and contextual-data invariants.
