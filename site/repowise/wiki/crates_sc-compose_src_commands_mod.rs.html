Overview

commands/mod.rs is the CLI-layer command-module aggregator and shared presentation/error adapter, exposing command submodules while converting template-pack data and failures into consistent terminal or JSON output. main.rs consumes this module as the CLI entry point; examples.rs and templates.rs consume its shared helpers to keep equivalent command paths behaviorally aligned.

The module declares the command surface for composition, dispatch, examples, reports, template initialization, templates, verification, and workspace operations. Its private helpers centralize repeated CLI concerns that would otherwise diverge across subcommands:

  • Formatting template-pack lists for human-readable and JSON output.
  • Assigning stable diagnostic codes to expected configuration and template-store failures.
  • Attaching actionable recovery hints, such as a list command, environment-variable guidance, or a path to inspect.
  • Preserving the original anyhow::Error as the underlying command error.

Although the helper functions are private to the commands module, Rust descendant-module visibility allows examples.rs and templates.rs to import and reuse them.

Shared internal helpers

print_pack_list(packs: &[TemplateMeta], json: bool) -> anyhow::Result<()>

Renders a collection of template metadata in one of two output formats:

  • With json == true, emits one JSON object through the crate-wide print_json path:

json { "packs": [ { "name": "example-name", "path": "normalized/path" } ] }

  • With json == false, prints one pack per line. The line includes whichever optional metadata is available:

text name - description (version) name - description name (version) name

The JSON representation intentionally includes only name and path; descriptions and versions are presentation-only in the current text format. Paths are passed through to_forward_slash, ensuring JSON output is stable across Windows and Unix-like systems.

Callers:

  • run_examples_list
  • run_templates_list

Both map any output failure to CommandError::usage.

pack_not_found_error(kind, name, list_command) -> CommandError

Builds a structured usage error for an absent example or template pack:

  • Diagnostic code: ErrConfigPackNotFound
  • Error message: "{kind} pack{name}was not found"
  • Recovery hint: run the supplied list command

Examples and templates provide distinct values for kind and list_command, allowing one helper to produce context-specific guidance:

example pack `starter` was not found
recovery: run `sc-compose examples list`

store_root_error(error, env_var) -> CommandError

Converts failure while resolving a template-store root into a configuration parse error:

  • Diagnostic code: ErrConfigParse
  • Recovery hint: review configuration by setting the named environment variable

examples supplies SC_COMPOSE_DATA_DIR; templates supplies SC_COMPOSE_TEMPLATE_DIR. The &'static str parameter makes these environment-variable labels fixed program constants rather than dynamically sourced values.

pack_not_renderable_error(error) -> CommandError

Converts a pack-discovery or pack-loading error into a non-renderable-pack error:

  • Diagnostic code: ErrConfigPackNotRenderable
  • Recovery hint: add a .j2 file to the template-pack directory

This is used where a store can find a pack directory but cannot produce a usable renderable pack from it.

template_exists_error(destination: PathBuf) -> CommandError

Builds the error returned when adding a user template would overwrite an existing pack:

  • Diagnostic code: ErrConfigTemplateExists
  • Error message includes the destination path.
  • Recovery hints instruct the user to inspect that path, then delete the existing template or choose a different name.

PathBuf is accepted by value because the same destination is moved into the InspectPath recovery hint after it is rendered into the error message.

Usage Notes

Listing packs

A list command resolves a TemplateStore, retrieves metadata, and delegates output formatting:

  1. run_examples_list or run_templates_list creates the relevant store.
  2. Store-root resolution failures are mapped with store_root_error.
  3. The store returns Vec<TemplateMeta>.
  4. print_pack_list selects text or JSON based on ListArgs.json.
  5. Output failures become generic usage errors at the caller boundary.

For text output, optional fields determine the printed form. Consumers should not parse this format as a stable data interface; use --json where automation needs structured data.

JSON path portability

The list JSON uses slash-normalized paths even on platforms where PathBuf::display() would use backslashes. This makes output easier to compare in scripts, snapshots, and cross-platform documentation.

A potential pitfall is assuming JSON path strings preserve native filesystem separators. They deliberately do not; they are normalized for output consistency.

Error classification and recovery

Expected user-correctable failures should flow through the appropriate factory instead of being wrapped as an unclassified CommandError::usage:

Condition Helper Result
Requested example/template is absent pack_not_found_error ErrConfigPackNotFound plus a command to list available packs.
Store root cannot be resolved store_root_error ErrConfigParse plus environment-variable guidance.
Pack contains no renderable template pack_not_renderable_error ErrConfigPackNotRenderable plus .j2 guidance.
Adding a template collides with an existing destination template_exists_error ErrConfigTemplateExists plus path inspection and replacement guidance.

This distinction matters for both CLI users and machine consumers: the diagnostic code identifies the failure category, while recovery hints provide the recommended next action.

Extending commands

When adding a command module:

  1. Add a pub(crate) mod <name>; declaration here.
  2. Keep command-specific control flow in its own module.
  3. Reuse these shared helpers when the new command has equivalent pack-list or template-store failure semantics.
  4. Add a new helper only when it represents a distinct, reusable diagnostic contract with its own code and recovery guidance.

Avoid putting command parsing, rendering-library logic, or template-store implementation in this file. Its responsibility is command namespace composition and shared CLI adaptation, not command execution.

Empty and partial metadata

print_pack_list handles an empty slice without special output: text mode prints no lines, and JSON mode emits {"packs":[]}. For individual packs, absent descriptions or versions do not create placeholder text; only available metadata is shown. This avoids exposing Option-style implementation details to users.
