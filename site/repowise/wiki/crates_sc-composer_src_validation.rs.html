Overview

The Application-layer validation module is the template-variable discovery and validation orchestrator: it consumes a ComposeRequest, expanded template, and resolution result to produce a ValidationReport plus internal ValidationState.

It merges declarations, required paths, and defaults from root and included frontmatter; overlays template defaults, environment values, explicit input, and render-time built-ins; then emits diagnostics for empty bodies, malformed frontmatter, missing required values, undeclared references, unused defaults, and extra inputs.

This is a high-activity, high-complexity hotspot. Changes can alter validation behavior across the Rust library, CLI, and Python bindings; preserve diagnostic codes, precedence rules, include-chain attribution, and per-pass token semantics.

ValidationState keeps both the effective render context and provenance metadata. Provenance supports informational “default used” diagnostics, while origin and include-chain maps let required-variable failures point back to the declaring template.

Token discovery is intentionally lightweight rather than a full template parser. It scans expression and statement delimiters, recognizes {% for … in … %} scopes, excludes loop-bound locals, and collects valid VariableName references. Multi-pass templates are scanned independently using the brace count associated with each pass, preventing {{ … }} and {{{ … }}} expressions from being confused.

Required-variable validation supports dotted paths such as pr.number. It traverses JSON objects, applies the same path requirement to every array member, distinguishes absent top-level values from missing nested fields, and reports scalar/object shape mismatches separately.

Public API

  • BUILTIN_VARIABLE_NAMES: [&str; 5] exposes the render-context names injected for every render:
  • TEMPLATE_NAME
  • HOSTNAME
  • USERNAME
  • RENDER_DATE

  • RENDER_TIMESTAMP

  • discover_tokens(text: &str) -> BTreeSet<VariableName> discovers references in standard {{ ... }} expressions.

  • discover_tokens_with_brace_count(text, brace_count) -> BTreeSet<VariableName> discovers references for a specified expression-delimiter width. Counts below two return an empty set. Exact-delimiter handling prevents a lower-brace scan from matching a higher-brace expression.

  • discover_all_pass_tokens(parsed) -> BTreeMap<usize, BTreeSet<VariableName>> returns references per parsed pass. Each pass uses pass_number + 1 braces.

Internal application entry points include:

  • validate_expanded, which constructs the report and partitions diagnostics into warnings and errors.
  • collect_validation_state, which computes effective values, declarations, sources, origins, and pass-scoped metadata.
  • inject_builtin_vars, which supplies runtime values after validation-state collection.
  • validate_required_path, which checks dotted required paths against JSON input values.

Dependencies

The module depends on:

  • types for requests, policies, variable names/sources, input values, and validation reports.
  • frontmatter for parsed template passes and defaults/required-variable declarations.
  • diagnostics for structured severity, code, path, location, and include-chain reporting.
  • ExpandedTemplate and ResolveResult from the composition pipeline.
  • serde_json for structured input traversal and default serialization.
  • time for date and RFC 3339 timestamp built-ins.
  • Standard ordered collections (BTreeMap, BTreeSet) for deterministic state and diagnostic behavior.

It is called as part of the broader validation flow exposed by the library and consumed by the CLI and Python bindings.

Usage Notes

A normal validation flow is:

  1. Resolve and expand the requested template, including nested includes.
  2. Call the library validation entry point, which invokes this module’s validate_expanded.
  3. Inspect ValidationReport.ok, errors, and warnings.
  4. If rendering proceeds, inject built-ins into the collected state so the renderer receives the completed context.

Variable precedence is ordered so later sources replace earlier ones:

  1. Included and root frontmatter defaults establish initial values.
  2. Request-level defaults replace frontmatter values.
  3. Environment values replace defaults.
  4. Explicit input replaces environment values.
  5. Built-ins replace defaults but preserve environment and explicit-input values.

Structured values replace whole top-level values; they are not deep-merged. For example, input { "pr": { "number": 43 } } replaces a default pr object rather than retaining default sibling fields.

Unknown provided variables are compared at the top-level boundary. Supplying pr.url data within a declared pr object is allowed, while an unrelated top-level input can be ignored, warned about, or rejected according to UnknownVariablePolicy.

For required array paths such as sprints.id, every array member must satisfy the nested path. An empty array is considered satisfied because no member violates the requirement.

Be careful when extending identifier collection: it is lexical and scope-aware, not a full MiniJinja AST traversal. New statement forms, binding syntax, or identifier-like literals may require updates to KEYWORDS, loop-scope parsing, and delimiter tests.
