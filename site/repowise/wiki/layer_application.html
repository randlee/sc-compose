Overview

The Application layer is the template-composition orchestration layer: it turns caller inputs, template files, configuration, and profiles into validated rendered artifacts, structured results, and stable diagnostics for the CLI and Python binding surfaces.

Its central public boundary is sc-composer, a pure Rust library that exposes composition, rendering, resolution, validation, verification, frontmatter parsing, include expansion, workspace initialization, and observation APIs. The layer owns the application-facing contracts that make these capabilities usable consistently across interfaces: typed requests and results, policies, validation rules, diagnostic envelopes, error families, and portable path serialization.

The layer has six edge connectors. crates/sc-composer/src/lib.rs is the primary library façade; types.rs and diagnostics.rs define the shared machine-facing contract; crates/sc-compose/src/path_utils.rs and command_error.rs adapt that contract to CLI output and process exit behavior; and bindings/python/src/errors.rs adapts failures to typed Python exceptions. The Python package initializer re-exports the native binding surface as the Python-facing API.

Key Components

  • crates/sc-composer/src/lib.rs
    Public application entry point. It re-exports the composition pipeline—compose, render_all, validate, verify, profile resolution, include expansion, frontmatter support, observers, diagnostics, errors, and typed contracts—so callers depend on a coherent library API instead of internal modules.

  • crates/sc-composer/src/types.rs
    Defines the value model that crosses the layer boundary: ComposeRequest, ComposeResult, policies, modes, profile and runtime types, pass configuration, validation reports, resolution and verification results, and validated names and confinement roots. It also validates structured input values and converts YAML inputs into supported render-context values.

  • crates/sc-composer/src/diagnostics.rs
    Provides versioned, machine-readable diagnostics through Diagnostic, DiagnosticEnvelope, severity levels, and stable ERR_*, WARN_*, and INFO_* codes. This keeps automation and user interfaces independent of unstable human-readable error text.

  • crates/sc-composer/src/error.rs
    Normalizes failures from resolution, includes, validation, rendering, and configuration into crate-owned ComposeError variants. These errors preserve domain context and can expose a stable diagnostic code and recovery guidance.

  • crates/sc-composer/src/path_utils.rs
    Converts paths to forward-slash strings, removing platform-specific path representations from serialized output, diagnostics, and binding-facing values.

  • crates/sc-compose/src/path_utils.rs
    Applies CLI-specific path rules: relative-path validation, normalization, and serde serialization of individual and optional paths or path collections.

  • crates/sc-compose/src/command_error.rs
    Converts application errors into CLI behavior: exit codes, diagnostic collections, and recovery hints. It distinguishes usage/configuration failures from validation or rendering failures while preserving structured diagnostics.

  • bindings/python/src/errors.rs and bindings/python/python/sc_compose/__init__.py
    Translate library failures into typed Python exception classes such as ScValidationError and ScResolveError, exposing message and optional code attributes. The package initializer then presents the native composition API as a stable Python import surface.

  • prototype/multipass/types.py
    Documents the conceptual multi-pass model: pass headers describe required variables, defaults, metadata, and delimiter depth; parsed templates retain stacked headers and body content; render contexts carry pass-specific variables. This aligns with the Rust layer’s pass configuration and staged rendering concepts.

Data Flow

  1. A caller enters through the CLI, Python bindings, or directly through the sc-composer library façade.

  2. The Application layer converts raw inputs into typed contracts. Configuration, profile names, variable names, render values, paths, composition mode, and policy are validated before pipeline execution.

  3. The composition pipeline resolves the requested template or profile, parses frontmatter, expands includes within confinement rules, and merges caller inputs with defaults and pass-specific context.

  4. Validation discovers referenced variables and checks required inputs, undeclared tokens, supported value shapes, and policy constraints. Diagnostics may be emitted for defaults used, conflicting declarations, or invalid content.

  5. Rendering executes the resolved template for the selected pass or passes, producing rendered artifacts and composition results. Verification can compare or assess generated output as a subsequent application operation.

  6. Successful results are returned through shared Rust types and serialized with portable forward-slash paths. Observers can receive pass, resolution, include, render, validation, and verification events without changing the core workflow.

  7. Failures flow through ComposeError and structured diagnostics. The CLI maps them to exit codes and recovery hints; the Python binding maps them to typed Sc*Error exceptions; direct library consumers retain the crate-owned error and diagnostic model.

Architecture Notes

The Application layer is deliberately interface-neutral at its core. sc-composer remains a pure rendering and composition library, while CLI parsing and process concerns stay in sc-compose, and Python exception mechanics stay in the binding crate. This preserves the intended dependency direction: interface layers consume the library rather than embedding interface concerns inside it.

The layer depends lightly on the CLI and Types layers, while the CLI is its primary consumer, followed by Types and tests. That import pattern reflects its role as the execution and contract boundary between input-facing interfaces and lower-level template-processing behavior.

Stable diagnostics are a first-class architectural contract. Consumers should use diagnostic codes, severity, envelope schema version, and structured fields for automation; messages remain useful for people but should not become the only integration point.

Path handling is intentionally split. The library provides canonical forward-slash formatting for cross-platform output, while the CLI owns stricter relative-path normalization and serialization rules. This lets all consumers receive stable paths without forcing CLI-specific filesystem policy into the pure library.

The multi-pass model treats each pass as a distinct rendering context with a corresponding delimiter depth. Parsed templates retain remaining pass headers until fully rendered, allowing staged composition while keeping pass requirements and defaults explicit.
