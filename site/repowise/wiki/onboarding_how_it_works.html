How It Works

What this system does in one sentence

sc-composer provides profile resolution for consumers, while sc-compose and the Python bindings expose entry points around that capability.

A walk through one example

When a consumer calls crates/sc-composer/src/resolver.rs::resolve_profile, resolution proceeds through resolve_profile_with_observer and then resolve_profile_impl.

The implementation identifies possible locations through candidate_directories, then builds the applicable sequence through runtime_chain. That sequence is expressed using crates/sc-composer/src/types.rs::RuntimeKind, which carries the runtime distinction used by the resolution path.

The same library sits behind other entry surfaces: crates/sc-compose/src/main.rs::main reaches crates/sc-compose/src/cli.rs::parse_cli and crates/sc-compose/src/cli.rs::Cli, while bindings/python/src/lib.rs provides another entry point into the package surface.

Why it's shaped this way

The resolution flow is concentrated in sc-composer, with its public-facing entry points separated from the CLI and Python binding entry points. This lets consumers enter through different surfaces while following the same resolver path and shared RuntimeKind representation.
