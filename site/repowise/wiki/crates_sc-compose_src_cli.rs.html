File: crates/sc-compose/src/cli.rs

Overview

cli.rs is the Application-layer command-line parser and edge connector that consumes process arguments and produces typed Cli command configurations for dispatch, rendering, validation, verification, workspace setup, template-pack management, and reports. It is imported across layer boundaries by command handlers and request-building code, so its argument types form the CLI-facing contract for much of sc-compose.

This is a hotspot for both change frequency and complexity. Changes to flag names, defaults, conflicts, flattening, or parsing behavior can affect multiple commands at once and can break scripting compatibility.

The module uses clap derives to define the visible CLI surface:

  • Cli is the root parser for the sc-compose executable.
  • Command selects one top-level workflow.
  • Reusable argument groups (InputArgs, CommonArgs, and RenderBehaviorArgs) keep shared behavior consistent across commands.
  • Value enums constrain resolution mode, profile kind, AI runtime, and handling of unknown input variables.
  • parse_cli applies preprocessing before Clap parses arguments.
  • parse_pass_inputs separately extracts pass-scoped inputs, which are intentionally not represented in Clap’s normal argument grammar.
  • command_wants_json provides a single dispatch-friendly way to identify JSON output requests, including nested subcommands.

Public API

All items are pub(crate): they are available throughout the sc-compose crate but are not exported as a public library API.

Root command model

Symbol Role
Cli Root Clap parser containing the selected Command.
Command Top-level subcommand enum: Render, Resolve, Validate, Verify, TemplateInit, FrontmatterInit, Init, ObservabilityHealth, Examples, Templates, and Reports.
parse_cli() Parses filtered process arguments into Cli.
command_wants_json(&Command) Returns whether the selected command/subcommand requested machine-readable JSON output.

Two hidden variants, ReportRenderMany and ReportCatalog, support report workflows without advertising those commands in normal help output.

Shared argument groups

InputArgs collects values supplied to template rendering:

  • --var key=value appends explicit variables.
  • --var-file PATH appends JSON or YAML variable-object sources.
  • --env-prefix PREFIX imports matching environment variables.
  • --strict rejects undeclared referenced variables.
  • --unknown-var-mode error|warn|ignore controls reporting for supplied variables that are not consumed.

CommonArgs defines source resolution for render-like operations:

  • --mode file|profile, defaulting to file.
  • --kind agent|command|skill, used in profile mode and defaulting to agent.
  • --agent NAME and alias --agent-type NAME.
  • --runtime / --ai runtime selector.
  • Flattened InputArgs.
  • --root PATH, defaulting to the current directory.
  • --file PATH, used in file mode.

RenderBehaviorArgs defines output presentation:

  • --output PATH writes instead of stdout.
  • --guidance / --guidance-file append guidance content.
  • --prompt / --prompt-file append prompt content.
  • --json selects machine-readable output.
  • --dry-run reports the target without writing it.

Supporting enums and parsers

  • Mode: Profile or File.
  • Kind: Agent, Command, or Skill.
  • Ai: Claude, Codex, Gemini, or Opencode.
  • UnknownVarMode: Error, Warn, or Ignore.
  • PassInputArgs: one --pass group with its pass number, explicit variables, and variable files.
  • parse_var(input): parses one key=value pair, rejecting an input without =.
  • parse_pass_inputs(command_name): scans raw process arguments for repeated pass-specific input groups.
  • filtered_args_for_clap(): removes pass-scoped syntax before invoking Clap.

Dependencies

  • clap supplies Parser, Subcommand, Args, and ValueEnum derives, plus argument actions, validators, aliases, conflicts, and generated help.
  • anyhow::Result is used for the local parser result signature.
  • std::ffi::OsString preserves native argument encoding while filtering raw process arguments.
  • std::path::PathBuf represents workspace, template, output, deployed-file, and import paths.
  • crate::commands::reports supplies report command argument types and subcommands.

The module is consumed by main.rs and multiple command/request modules:

  • commands::dispatch consumes Cli to route execution.
  • commands::compose uses render/output and delimiter options.
  • render_request converts common/input/render fields into concrete rendering requests, variable sources, and confined roots.
  • commands::verify adapts common arguments for verification.
  • commands::examples, commands::templates, commands::template_init, and commands::workspace consume their corresponding argument types.

Usage Notes

Basic file rendering

sc-compose render --file templates/agent.md --var name=Riley

RenderArgs combines CommonArgs with RenderBehaviorArgs, so the command resolves the file under the default workspace root, supplies name, and emits rendered text to stdout.

To write a target instead:

sc-compose render \
  --file templates/agent.md \
  --var name=Riley \
  --output generated/agent.md

Profile-based resolution

sc-compose resolve \
  --mode profile \
  --kind agent \
  --agent reviewer \
  --runtime codex \
  --root .

--agent-type is accepted as an alias for --agent. Callers should avoid supplying ambiguous combinations of profile-only inputs and file-mode inputs unless downstream command semantics explicitly support them.

Input precedence and validation

sc-compose validate \
  --file templates/prompt.md \
  --var audience=engineers \
  --var-file inputs/common.yaml \
  --env-prefix SC_ \
  --strict \
  --unknown-var-mode warn

This module only captures the input sources and policies. render_request and related code load files/environment variables and enforce their operational meaning. parse_var intentionally splits only at the first =, so values may themselves contain equals signs:

sc-compose render --file template.md --var callback=https://example.test/?a=b

An empty key or value is not rejected here if the input contains =; later validation, if any, owns that policy.

Multi-pass arguments

Pass-specific values use raw-argument scanning:

sc-compose render \
  --file templates/stacked.md \
  --pass 1 --var title=Draft --var-file inputs/pass-1.yaml \
  --pass 2 --var title=Final --var-file inputs/pass-2.yaml

filtered_args_for_clap removes --pass, the following pass number, and --var / --var-file values inside a pass group before ordinary Clap parsing. parse_pass_inputs("render") then reconstructs groups from the original argument list.

Important constraints:

  • --var and --var-file in a pass group must follow --pass; otherwise parse_pass_inputs returns an error.
  • Both separated (--pass 2) and equals (--pass=2) forms are accepted.
  • Pass numbers must parse as u8.
  • The filtering logic recognizes pass groups only after render, validate, verify, or template-init.
  • Unrelated flags terminate the current pass-group filtering state, so changes to argument ordering or new flags near pass syntax require regression tests.

This split parsing is a compatibility-sensitive implementation detail: Clap should receive only the normal command grammar, while pass-specific data remains available to multi-pass handlers.

Custom delimiters

sc-compose render --file template.md --brace-count 3

or:

sc-compose render \
  --file template.md \
  --variable-delimiters '<<' '>>'

These choices are mutually exclusive, and both conflict with --all. The conflict declarations prevent combinations whose semantics would be unclear when rendering stacked template passes.

JSON output

Use JSON consistently for automation:

sc-compose templates list --json
sc-compose reports index --json
sc-compose verify --file template.md deployed/output.md --json

command_wants_json centralizes the decision across top-level commands, nested examples/templates subcommands, report subcommands, and hidden report helpers. When adding a new command or a new JSON-bearing nested subcommand, update this match or dispatch may choose the wrong output/error format.

Examples and template packs

sc-compose examples list
sc-compose examples starter --var project=sc-compose
sc-compose templates add ./my-pack my-pack
sc-compose templates list --json
sc-compose templates my-pack --output generated.md

ExamplesArgs and TemplatesArgs use args_conflicts_with_subcommands, which prevents a positional pack name from being accidentally interpreted alongside list or add. Their no-subcommand mode means “render the named pack”; their subcommand mode means management/listing behavior.

Maintenance guidance

Because this file is a high-activity, high-complexity public edge of the application:

  • Preserve existing flag names, aliases, defaults, and output-mode behavior unless intentionally making a CLI compatibility change.
  • Add tests for both Clap parsing and raw pass parsing whenever modifying --pass, --var, --var-file, or supported command names.
  • Keep argument-group flattening aligned with consumers in render_request, compose, and verify.
  • Ensure every new JSON-capable command path is represented in command_wants_json.
  • Prefer explicit Clap conflicts and value parsers over relying on downstream handlers to reject invalid combinations.
