File: crates/sc-compose/src/observer_impl.rs

Overview

observer_impl.rs is the Application-layer edge connector that consumes sc-composer lifecycle and observation events and produces validated structured log events through sc-observability. As an imported cross-layer interface, it gives command dispatch, verification, and workspace flows one concrete observer that translates composition activity into durable CLI telemetry.

The central CliObserver owns an optional logger state and implements three observer-facing contracts:

  • CompositionObserver converts resolution, include expansion, validation, and rendering outcomes into log records.
  • ObservationSink dispatches ObservationEvent variants from sc-composer hooks to the corresponding observer methods.
  • CommandLifecycleObserver records command start/end metadata, including exit status, elapsed time, JSON mode, and diagnostic details.

This is a hotspot file: it combines frequent change activity with relatively high behavioral complexity. Changes can affect cross-layer command behavior, log schema compatibility, shutdown durability, operational health reporting, and failure-path observability.

Public API

Most symbols are pub(crate), making them internal to the sc-compose crate but available to command modules and the binary entry point.

Symbol Role
CommandStartEvent Command lifecycle payload containing command_name and json_output.
CommandEndEvent Completion payload containing command name, exit code, success state, elapsed time, output mode, and optional diagnostic data.
CommandLifecycleObserver Internal abstraction used by command orchestration to report command start and completion.
CliObserver::new(logger) Constructs the concrete observer around a running sc_observability::Logger.
CliObserver::health() Returns current logger health, including stopped-state health after shutdown. If internal state is unexpectedly absent, returns an unavailable report.
CliObserver::shutdown() Transitions a running logger to Logger<Stopped>, flushing it through Logger::shutdown(). It is idempotent.
CompositionObserver implementation Logs resolve attempts/outcomes, include outcomes, validation outcomes, and render outcomes.
ObservationSink::emit() Matches an ObservationEvent and forwards it to the corresponding composition-observer hook.
CommandLifecycleObserver implementation Logs compose.command/started and either compose.command/completed or compose.command/failed.

Drop calls shutdown(), so callers normally do not need a separate cleanup path. Explicit shutdown remains useful when callers must inspect final health or read the flushed log file before the observer is dropped.

Dependencies

  • sc-composer
  • Supplies CompositionObserver, ObservationSink, ObservationEvent, and the pipeline event payloads.

  • CliObserver is the adapter that makes core composition events observable from the CLI layer.

  • sc-observability

  • Supplies Logger, typed log-envelope fields, timestamps, process identity, schema versioning, and shutdown-state typing.

  • Logger::log() performs writes; this file deliberately does not use the deprecated compatibility emit() path.

  • sc-observability-types

  • Supplies health-report, writer-state, query-health, diagnostic-summary, and label-validation types.

  • crate::observability::SERVICE_NAME

  • Defines the stable service identifier used in every emitted event.

  • crate::path_utils::to_forward_slash

  • Normalizes paths before serialization so emitted path fields are portable and consistent across platforms.

Primary consumers are main.rs and the command modules (dispatch.rs, verify.rs, and workspace.rs), which use this implementation as the CLI-facing observer.

Usage Notes

Construct the observer once the CLI logger has been configured, then pass it into command orchestration wherever a composition or command-lifecycle observer is accepted.

let logger = Logger::builder(config)?.build();
let mut observer = CliObserver::new(logger);

observer.on_command_start(&CommandStartEvent {
    command_name: "render".to_owned(),
    json_output: false,
});

// Pass `observer` to composition/dispatch code, which emits pipeline events.

observer.on_command_end(&CommandEndEvent {
    command_name: "render".to_owned(),
    exit_code: 0,
    success: true,
    elapsed_ms: 42,
    json_output: false,
    diagnostic_code: None,
    diagnostic_message: None,
});

observer.shutdown();
let health = observer.health();

Important behavior and pitfalls:

  • Observer calls are intentionally non-failing. emit_log() ignores Logger::log() errors, allowing the primary command flow to continue even when logging sinks fail. Inspect health() for dropped events, flush failures, or the most recent error.
  • shutdown() is safe to call repeatedly. A stopped logger is retained so final health remains queryable and no second shutdown is attempted.
  • If logger is unexpectedly None, health() returns an explicit unavailable health report with a stopped writer and unavailable query state.
  • Invalid static event labels do not prevent log emission. The requested invalid values and validation errors are recorded in fields, while target/action/outcome fall back to compose.observability, degraded, and failure.
  • Resolution and include paths are converted to forward-slash strings before logging. Preserve this normalization when adding new path-bearing fields.
  • Failure records include the available diagnostic code; command and validation events can additionally include diagnostic messages. Avoid placing unbounded or sensitive input directly into log fields.
  • The ObservationSink dispatcher includes pass and verify variants, but this file only provides local logging implementations for the resolution, include, validation, and render hooks. Any pass/verify behavior follows the CompositionObserver contract’s available defaults or implementations.
  • schema_version() and service_name() panic only if crate-owned constants violate the observability newtype validation rules. Treat such failures as configuration/schema regressions rather than runtime input errors.
